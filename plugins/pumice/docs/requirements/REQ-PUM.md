# REQ-PUM — Pumice 要件定義

> 最終更新: 2026-09-01

## 概要

Pumice は**単体ボーカルトラックの動的共鳴抑制**。1 本の声に挿して、狙いは 1 つ。

> **周囲より突出した帯域を、突出した瞬間だけ削る。**

静的な EQ で削ると鳴っていない間まで痩せ、コンプで潰すと全帯域が動く。
**周波数と時間の両方で狙う**のがこの製品。

**当初の主張は「その声が持っている『毎回同じ周波数で出っ張る』場所を
選んで削る」だった。それは達成できなかった**（`REQ-PUM-003`、
`PUM-10c` で v1 から落とした）。何を測って何が失敗したかは
`REQ-PUM-003` にそのまま残してある。

対象は Bitwig / Ableton Live / Reaper / Studio One。**AU は対象外**
（`REQ-PUM-014`）。

## この製品がラインで初めてやること

**音声パスに FFT を置く**（`REQ-PUM-007`）。`nxe_dsp::spectrum` は
「FFT ではなくバンドパス列」と書き、Sparkleur は spectral flux を
「FFT を音声パスに置くことになる」で却下した。**どちらも、もっと安いもので
同じ仕事ができたから却下している**。ここは安いもので同じ仕事ができない
初めてのケースなので、例外として通す。理由は
`docs/specifications/architecture.md` に残す。

**レイテンシを申告する**（`REQ-PUM-007`）。既存 5 本はすべて報告 0。
**これがこの製品のゲート**で、`DBL-2` と同じ扱い — 4 ホストで PDC が
効かなければ方式ごと選び直す。

**「ビット一致」を約束しない**（`REQ-PUM-012`）。5 製品共通だった
「`MIX` = 0 でビット一致」は、オーバーラップアドの浮動小数の丸めがある以上
成立しない。**約束の文言が変わる初めての製品**。

## 設計の中心にある 4 つの判断

**共鳴と倍音を分ける機構は無い**（`REQ-PUM-003`)。時間で分けようとして
失敗した — 詳細はそちら。**代わりに `THRESHOLD` を出した**：どれだけ突出したら
反応するかを人が決める。soothe が `SELECTIVITY` でやっているのと同じ形で、
**それを避けるのがこの製品の主張だったので、主張が 1 つ減っている**。

**ノードは削減量の重みであって、EQ ではない**（`REQ-PUM-004`）。ノードは
「ここはもっと削れ」「ここは守れ」を周波数の関数として書くもので、
それ自体は何のゲインも動かさない。`DEPTH` = 0 ならノードが何本あっても
出力は変わらない。

**専用のディエッサを持たない**（`REQ-PUM-020`）。歯擦音は「周波数はほぼ同じ／
時間的には断続」で、`REQ-PUM-003` の機構がそのまま当たる形。専用の閾値と
時定数を別に持つと、Sparkleur の `protect.rs` が書いているとおり
「既に動いている一つ目の隣に、歩調を合わせ続ける二つ目」を置くことになる。

**`STATIC` を残す**（`REQ-PUM-003`）。長期平均を切ると soothe と同じ
「平滑スペクトルとの比較」になる。**適応が裏目に出る素材があるはず**で、
そのとき逃げ場が無いと製品が使えなくなる。Sparkleur の `MODE` と同じ位置。

## REQ-PUM-001: トポロジと原音の扱い

- **優先度**: Must
- **ステータス**: Draft
- **説明**: 並列。dry は STFT を通らない。

```text
Input ─┬─ delay(latency) ───────────────── dry ──────┐
       │                                             ├─ MIX ─ OUTPUT ─ Out
       └─ STFT ─ 検出 ─ ゲイン ─ iSTFT ──── wet ─────┘
```

- **dry ディレイラインは必須**。持たないと dry と wet が申告レイテンシぶん
  ずれ、`MIX` のクロスフェードが櫛形になる。**透明性のためではなく
  `MIX` のために持つ**。
- **`DEPTH` = 0 で経路を迂回しない**（`REQ-SPK-001` / `REQ-GLU-001` と同じ）。
  オートメーションで 0 を離れた瞬間に不連続が出るのを避ける。`DEPTH` = 0 の
  wet は「全ビンのゲインが 1 の再構成」で、入力と数値的に一致はしないが
  **−120 dB 以下**（`REQ-PUM-012`）。
- **受入条件**:
  - [ ] `MIX` = 0 で出力が**遅延した入力とビット一致**（dry 経路の帰結）
  - [ ] `DEPTH` = 0 で出力と遅延入力の差が **−120 dB 以下**
  - [ ] `DEPTH` を掃引して不連続が出ない
  - [ ] dry の遅延がホストへ申告した値と**サンプル単位で一致**
- **依存**: REQ-PUM-007

## REQ-PUM-002: DEPTH

- **優先度**: Must
- **ステータス**: Draft
- **説明**: 削減量の主軸。**この製品で最初に回すノブ。**

- **`DEPTH` はノード曲線に掛かる。** ノードは重みを作り、`DEPTH` がその全体の
  大きさを決める。だから `DEPTH` = 0 は**ノードが何本あってもちょうど何もしない**。
- **`DEPTH` を上げてもラウドネスが跳ねない。** 削る製品なので下がるのは当然
  だが、**下がり方が素材によって暴れない**こと。`OUTPUT` で戻すのは人の仕事。
- ノードが 0 本のとき、重みは**動作範囲全体で一様**。挿した瞬間に
  `DEPTH` だけで成立する必要がある（`REQ-PUM-024`）。
- **受入条件**:
  - [ ] `DEPTH` = 0 で全ビンのゲインがちょうど 1
  - [ ] `DEPTH` を掃引して最大削減量が単調に増える
  - [ ] ノード 0 本で、動作範囲内の削減の重みが平坦（±0.1 dB）
- **依存**: REQ-PUM-003, REQ-PUM-004

## REQ-PUM-003: 共鳴の検出（適応は落とした）

- **優先度**: Must
- **ステータス**: Decided（2026-09-01、`PUM-10c`）
- **説明**: 周波数方向にリング状の参照を置き、その超過量を短期フォロワで
  追って削る。**それだけ。**

```text
参照   ビンの周りを穴として抜いたリングの平均パワー（穴の幅 = SHARPNESS）
超過   e[k] = 10·log10( 平滑した |X[k]|² / 参照 )
WHEN   e[k] の非対称フォロワ（SPEED）
削減   clamp( SLOPE · (WHEN − THRESHOLD), 0, CEILING ) × 重み × DEPTH
```

- **入力ゲインに依存しない。** 検出は「ビンと参照の比」なので、分子と分母が
  一緒に動く。`nxe_audio::guard` が相対検出を選んだのと同じ理由。
- **普通の素材を触らない。** `THRESHOLD` の既定 4.5 dB は**測って決めた** —
  白色ノイズと歌の倍音がどちらもちょうど 0 dB を読む値（`SPK-18` の再発防止）。
- **`THRESHOLD` は控えめな既定であって答えではない**（`REQ-PUM-025`）。
- **受入条件**:
  - [x] `DEPTH` = 0 で全ビンのゲインがちょうど 1
  - [x] **広帯域ノイズの RMS 変化が 0.1 dB 未満**（`SPK-18` の再発防止）
  - [x] 削減量が入力ゲイン ±12 dB で 0.2 dB 以内
  - [x] `THRESHOLD` を上げると歌の倍音が守られる
- **依存**: REQ-PUM-005, REQ-PUM-006, REQ-PUM-007

### 適応的な検出（`ADAPTIVE` / `MODE`）を v1 から落とした

**これが製品の主張だった。** 「倍音は音程で動き、共鳴は動かない」ので、
長期の統計量が**どこ**を、短期包絡が**いつ**を決める——単体ボーカルという
前提を置いて初めて使える仮定で、だから汎用製品には入れられない、と書いていた。

**実装して、実機で聴いて、測って、成立しないことが分かった。**
`PUM-4` で通したゲートは**非現実的に持続的な素材で校正していた** — 18 dB の
ブーストを**常時**かけたノイズ。実際の共鳴は歌っている時間の一部しか
励起されない。

**3 つの統計量を試した。3 つとも分離しない。** 次に同じ着想を持つ人が
着想から始めないよう、測定値を残す。

**1. 超過量の長期平均**（実装したもの）。**間欠的な共鳴は持続的な倍音より
低く読む——順序が逆転している。**

| 2.5 kHz の平均超過量 | |
|---|---|
| 共鳴が常時鳴る | **+8.75 dB** |
| 共鳴が 50% の時間 | +2.69 dB |
| 共鳴が 25% の時間 | −1.03 dB |
| **歌の倍音（最悪）** | **+6.04 dB** |

**2. duty cycle**（近傍を超えている時間の割合）。分離しない — ノイズのビンは
定義上 5 割の時間で近傍より上、倍音のビンは 100% のものもある。

| 2.5 kHz の duty | 他の帯域の最悪 |
|---|---|
| 白色ノイズ 0.46 | 0.49 |
| 歌の鋸波 0.52 | **1.00** |
| 共鳴が常時 0.75 | **0.85** |

**3. 幅**（近傍への超過 − 遠いリングへの超過）。分離しない — **倍音の谷の
帯域が最も高い値を出す。**

| | 2.5 kHz の差 | 倍音の最悪の差 |
|---|---|---|
| 歌の鋸波 | 0.19 | **11.60** |
| + 共鳴 Q2 | 8.35 | 11.33 |
| + 共鳴 Q4 | 6.96 | 11.53 |
| + 共鳴 Q8 | 4.09 | 11.58 |

**耳も同じことを言った。** 「`ADAPTIVE` にすると何も Reduction しない。
図にも出てこない」（2026-09-01）。測定と耳が独立に同じ結論を指した。

**落とす判断の根拠は最初から書いてあった** — この節の旧版に:

> それでも倍音が削れるなら `ADAPTIVE` を落とし、製品は `STATIC` だけになる
> — そのとき Pumice は soothe の再実装であって「ボーカルの soothe」では
> なくなるので、**要件から書き直す**

**出荷前なのでパラメータ id はまだ自由**で、`MODE` を消せる最後の瞬間だった。

**代わりに `THRESHOLD` を出した**（`REQ-PUM-025`）。人が「どれだけ突出したら
反応するか」を決める。**soothe の `SELECTIVITY` と同じ形で、それを避けるのが
主張だったので、主張が 1 つ減っている。** 製品は「ボーカル向けの既定値と
動作範囲を持つ soothe 型」で、それは正直な説明。

**v2 で再挑戦するなら、4 つ目の統計量から始める。** 上の 3 つは測って
潰してある。ピッチ追従（`REQ-DBL-002` が和音とギターで却下した道）は
単体ボーカルなら成立する可能性があり、そこが唯一残っている当て。

## REQ-PUM-004: ノード

- **優先度**: Must
- **ステータス**: Draft
- **説明**: **6 本。** 削減量を周波数の関数として重み付ける。

| | 範囲 | |
|---|---|---|
| `freq` | 20 Hz–20 kHz（対数） | |
| `width` | 0.1–4 オクターブ | |
| `depth` | **−100%…+100%** | **マイナスが「守る」** |
| `enabled` | | 既定 off |

- **上限が 6 本なのは nih-plug の制約**。ホストのオートメーションは `#[id]` に
  紐づくので、実行時にパラメータは生えない。6 × 4 = 24 パラメータで、
  Sparkleur の per-band 25 個と同規模。
- **`depth` は双極**。「3 kHz の存在感は削らせない」はボーカルで実際に要る
  操作で、片極性では表現できない。
- **既定は 0 本**。プリセットを持たない方針（`REQ-PUM-024`）なので、
  挿した瞬間に `DEPTH` だけで成立する必要がある。ノードは**例外を作る道具**。
- **ノードは何のゲインも動かさない。** ノードは重み、`DEPTH` が量。
- **受入条件**:
  - [ ] `enabled` が全部 off で、重みが動作範囲内で平坦（±0.1 dB）
  - [ ] `depth` = 0 のノードが重みを変えない
  - [ ] `depth` < 0 のノードがその周波数の削減を**減らす**
  - [ ] ノードが重なったときの合成が連続（`freq` を掃引して段差が出ない）
  - [ ] `DEPTH` = 0 なら、どのノード設定でも出力が変わらない
- **依存**: REQ-PUM-002

## REQ-PUM-005: SHARPNESS

- **優先度**: Must
- **ステータス**: Draft
- **説明**: **参照の平滑幅。** 何と比べて「突出」と判定するか。

```text
広い（1 オクターブ）  なだらかな盛り上がりも対象になる
狭い（1/6 オクターブ） 細いピークだけが対象になる
```

- **ゲイン曲線の平滑とは別物**。ゲイン曲線の周波数方向の平滑は
  **musical noise（ワブリング）を防ぐ床**で、固定の内部値。ノブにはしない —
  「EQ っぽい音」と「電話っぽい音」を分けているのはそこだけなので、
  ユーザーが 0 にできてはいけない。
- **受入条件**:
  - [ ] `SHARPNESS` を上げると、広い盛り上がりへの削減量が単調に減る
  - [ ] `SHARPNESS` 全域で、細いピークへの削減量が 3 dB 以内しか動かない
  - [ ] `SHARPNESS` の全域で musical noise が出ない（ゲイン曲線の平滑が
        固定の床を下回らないことの帰結）
- **依存**: REQ-PUM-003

## REQ-PUM-006: SPEED

- **優先度**: Must
- **ステータス**: Draft
- **説明**: WHEN 側の時定数。attack と release を 1 本で振る。

- **時間分解能に床がある**（`REQ-PUM-020`）。ゲインの更新は hop ごと、
  ゲイン変化は窓幅ぶん滲む。`SPEED` の速い端はその床で止まる。
- Advanced で attack / release を個別に触れる（`REQ-PUM-009`）。
- **受入条件**:
  - [ ] `SPEED` を上げると削減の立ち上がりが単調に速くなる
  - [ ] 最速でも hop 未満の時定数を要求しない（要求しても床で止まる）
  - [ ] 44.1 / 48 / 96 / 192 kHz で同じ**秒**になる
- **依存**: REQ-PUM-003, REQ-PUM-008

## REQ-PUM-007: STFT とレイテンシ申告

- **優先度**: Must
- **ステータス**: Draft
- **説明**: オーバーラップアド。**ラインで初の FFT、初のレイテンシ申告。**

- **窓は Hann、オーバーラップは 75%**（hop = N/4）。時間変化するゲインを
  掛けるので、50% では継ぎ目が出る。
- **申告レイテンシは `N`。** 48 kHz `NORMAL` で 2048 サンプル = 42.7 ms。

  **当初 `N − hop` と書いていた。それは誤り**（2026-09-01）。出力サンプルは
  それを覆う最後のフレームが足されるまで確定せず、そのフレームは `N − 1`
  サンプル先に終わる。**オーバーラップはレイテンシを買い戻さない。**
  `StftHelper` が `N` を返しているのが正しく、**それを 10 ms 短くできると
  いう主張は撤回した**（`StftHelper` を使わない理由はライセンスと AU の道
  だけ、`REQ-PUM-015`）。
- **これがゲート。** 4 ホストで PDC が効かなければ FFT 方式ごと選び直す。
  `DBL-2` と同じ扱いで、**空に近いラッパのうちに確かめる**。
  ゲートの中身は「レイテンシを申告して、その分だけ実際に遅らせる」だけの
  ラッパ — PDC が効いていればトラックはずれない。
- **`QUALITY` の変更で申告値が変わる**（`REQ-PUM-008`）。再生中に変えて
  復帰することもゲートの条件に含める。
- **受入条件**:
  - [ ] **Bitwig / Ableton Live / Reaper / Studio One の 4 ホストで、
        CLAP と VST3 の両方が PDC で補償される**（無処理のトラックと
        位相が合う）
  - [ ] 再生中に `QUALITY` を変えて、音が復帰する
  - [ ] 申告値が `N` とサンプル単位で一致
  - [ ] 全ビンのゲインが 1 のとき、再構成誤差が **−120 dB 以下**
- **依存**: なし

## REQ-PUM-008: QUALITY

- **優先度**: Must
- **ステータス**: Draft
- **説明**: 3 段。**分解能とレイテンシの取引で、CPU の取引ではない。**

| | 48 kHz の N | ビン幅 | レイテンシ |
|---|---|---|---|
| `LOW` | 1024 | 46.9 Hz | 21.3 ms |
| **`NORMAL`** | **2048** | **23.4 Hz** | **42.7 ms** |
| `HIGH` | 4096 | 11.7 Hz | 85.3 ms |

- **`.non_automatable()` で宣言する。** オートメーション可能なままだと、
  ポイントごとに PDC 再計算が走って毎回グリッチする。ホストのパラメータ一覧
  には出るが、オートメーション対象にはならない。
- **`N` はサンプルレートに追従する**（`REQ-PUM-017`）。固定サンプル数だと
  96 kHz で分解能が半分になり、「レートで音が変わる」を踏む。**固定ビン幅**で
  決め、`N` は `sample_rate / 目標ビン幅` に**最も近い 2 の冪**。
- **確保は最大 N で 1 回**（192 kHz × `HIGH` = 16384）。`QUALITY` の変更は
  「使う長さ」を変えるだけで、音声パスに確保が来ない。
- **既定 `NORMAL` は永久に動かせない。** `QUALITY` は音も変えるので、
  Sparkleur の `mode` と同じ規律（`REQ-SPK-022`）。
- **受入条件**:
  - [ ] `.non_automatable()` が立っている（パラメータを走査するテスト）
  - [ ] 3 段とも申告レイテンシが `N` と一致
  - [ ] `QUALITY` の変更で `process()` が確保しない
  - [ ] 4 レート × 3 段の全組み合わせでビン幅が目標の ±10% 以内
- **依存**: REQ-PUM-007

## REQ-PUM-009: 二層パラメータモデル

- **優先度**: Must
- **ステータス**: Draft
- **説明**: メインの 5 本 + 3 つのモード + ノード、Advanced に偏差。

| メイン | 役 |
|---|---|
| `DEPTH` | 削減量 |
| `THRESHOLD` | どれだけ突出したら反応するか |
| `SHARPNESS` | 1 つの特徴とみなす幅 |
| `SPEED` | 時定数 |
| `LOW` / `HIGH` | 動作範囲の端 |
| `MIX` | Dry / Wet |
| `OUTPUT` | 最終ゲイン |

| モード | |
|---|---|
| `QUALITY` | `LOW` / `NORMAL` / `HIGH`（非オートメーション） |
| `DELTA` | 削っている物だけを聴く |

**`MODE` は無い**（`REQ-PUM-003`）。適応検出を落としたので選ぶものが無い。

- **Advanced に出すもの**: attack / release の個別値、**WHERE の学習時定数**、
  最大削減量（上限は超えられない、`REQ-PUM-023`）、動作範囲の端。
- **`LOW` / `HIGH`（動作範囲）はノードに畳んだ。** 端のノードがその役なので、
  独立したノブを置くと同じ段を 2 箇所から書くことになる
  （`GLUE` と `STACK` が同じ段を書く問題と同型、`REQ-GLU-009`）。
- **受入条件**:
  - [ ] メインの 5 本だけで一通りの抑制が作れる
  - [ ] Advanced の偏差が 0 のとき、メインの表どおりの値になる
  - [ ] 全パラメータにコントロールがある（`#[id]` を走査するテスト）
- **依存**: REQ-PUM-002, REQ-PUM-004

## REQ-PUM-010: ラインの中での語の一意性

- **優先度**: Must
- **ステータス**: Decided
- **説明**: ラインで既に意味を持つ語を、別の意味で使わない。

| 語 | どうするか |
|---|---|
| `AIR` | **使わない。** Velour / Sparkleur が持ち、Air が製品名 |
| `FOCUS` | **使わない。** Sparkleur ではクロスオーバー境界を動かす語 |
| `SPEED` | **使う。** Sparkleur と**意味が同じ**（時定数） |
| `DEPTH` | **使う。決着済み**（2026-09-01。下） |

### `DEPTH` は Diorama と重なるが、譲らない

**`REQ-GLU-010` の「新しい側が譲る」を、ここでは適用しない。** 理由を
書いておかないと、規則を知らずに破ったように見えるため。

**あの規則が守っていたのは `AIR` で、`AIR` は 3 重に埋まっていた** — Velour の
パラメータ、Sparkleur のパラメータ、そして**製品名**。Vocal Glue が 4 個目を
名乗ると、「AIR を上げて」がどの窓の話か決まらなくなる。

`DEPTH` は Diorama と 1 対 1 で、**同じ窓に並ぶことはない**。Diorama では
距離、Pumice では削減量で、どちらも「その窓で一番大きいつまみ」。
文脈が常に 1 つしかない語は、規則が防ごうとしていた曖昧さを作らない。

**譲る側のコストのほうが大きい。** soothe から来た人が最初に探す語が
`DEPTH` で、そこに別の語を置くと**製品が何をするものかを 1 つ余分に
説明しないと伝わらない**。プリセットを持たない方針（`REQ-PUM-024`）なので、
挿した人が最初に回すものが見つかることに製品が依存している。

代案は検討した — `SAND`（軽石の動作、製品名と一続き）、`TAME`、`SMOOTH`
（Smooth Operator と同名になる）、`EASE`、`AMOUNT`。**`SAND` が次点。**

- 製品名 `Pumice` は軽石。**形を変えずにざらつきだけを削り落とす道具**で、
  Velour と同じ「手触りのある物質」の語法。

## REQ-PUM-011: ステレオの扱いとバス構成

- **優先度**: Must
- **ステータス**: Draft
- **説明**: **2→2 と 1→1。**

- **1→1 がこの製品では主役級。** ボーカルトラックはモノで録られていることが
  多い。Air / Diorama の 1→2 はモノから像を作る製品の形で、ここは違う —
  像を作らず、通っているものを削る。
- **検波は L/R をビンごとに平均パワーで合成し、同じゲイン曲線を両チャネルに
  掛ける。** 片チャネルだけ動くと像が動く（`REQ-GLU-011`）。
  振幅ではなくエネルギーで合成するのは `nxe_audio::guard` と同じ理由。
- **M/S では処理しない。** 誰も要求していない軸を足すことになる。
- **受入条件**:
  - [ ] 2→2 と 1→1 のみが提示される
  - [ ] 片チャネルに寄った素材で定位が動かない
  - [ ] L と R に**同一の**ゲイン曲線が適用される
- **依存**: REQ-PUM-007

## REQ-PUM-012: ミックス・出力・透明性

- **優先度**: Must
- **ステータス**: Draft
- **説明**: `MIX`（0〜100%）、`OUTPUT`（±12 dB）。

- **「ビット一致」を約束しない。** オーバーラップアドは全ビンのゲインが 1 でも

| | 約束 |
|---|---|
| `MIX` = 0 | 遅延した入力との差が **−120 dB 以下** |

  - [ ] 上の 2 行が測って通る
  - [ ] `OUTPUT` = 0 dB で unity
  - [ ] `MIX` を掃引して不連続が出ない
- **依存**: REQ-PUM-001

## REQ-PUM-013: UI

- **優先度**: Must
- **ステータス**: Draft
- **説明**: 1 画面。規則は `.agents/rules/ui.md`。

- **主役は図（`NodeField`）。** 入力スペクトル、削減カーブ、ノード曲線、

  しか描けないので、ノードに数値ラベルは付けられない（`polar.rs` の傷）。
  `ui.md` の「status バーはポインタが乗っているものの 1 行を運ぶ」がこの用途。
- **受入条件**:
  - [ ] 全パラメータにコントロールがある（`#[id]` を走査するテスト）
  - [ ] 音が止まると表示が減衰して消える（3 秒以内に 0）
  - [ ] 窓の高さが部品から計算されている
  - [ ] `.class("root")` が根に付いている
  - [ ] 図の上でノードを掴んで動かすと、パラメータが動いた**あとで**点が動く
- **依存**: REQ-PUM-018

## REQ-PUM-015: コアのホスト非依存と共有 DSP

- **優先度**: Must
- **ステータス**: Draft
- **説明**: DSP は `pumice-core` に置き、フレームワークも Vizia も知らない。

| 使うもの | どこから |
|---|---|
| `realfft` | **新規依存**。MIT OR Apache-2.0 なので寛容側のまま |
| `nxe_audio::envelope` | WHERE / WHEN のフォロワ |
| `nxe_audio::DelayLine` | dry 経路 |
| OLA バッファと窓 | **`pumice-core` に自作** |

- **`nih_plug::util::stft::StftHelper` は使わない。** 実装は既にあるが、
  `nih_plug` は GPL 側（`LICENSING.md`）で、依存すると `pumice-core` が
  寛容側から移る。それは `<plugin>-core` の存在理由 —「将来 AU ラッパを
  別のフレームワークで書いたとき、同じコードを呼べる」— を壊す。
  **バッファリングがラッパ側にあると、AU ラッパはエンジンではなく骨組みごと
  書き直すことになる。**
- 副次的に、自作のほうが**申告レイテンシが 10 ms 短い**（`REQ-PUM-007`）。
  `StftHelper` は**答え合わせの相手**として使う。
- **`nxe-audio` には上げない。** 2 個目の客が要求するまで（`architecture.md`）。
  ただし**パラメータ構造体を知らない自立したモジュールとして書く**ので、
  移動はファイルの移動だけで済む（`REQ-VEL-015` と同じ）。
- **ライセンス**: `pumice-core` は **MIT OR Apache-2.0**、`pumice` は
  **GPL-3.0-only**。
- **受入条件**:
  - [ ] `pumice-core` が `nih_plug` にも Vizia にも依存しない
  - [ ] `pumice-core` の依存が `nxe-audio` と `realfft` だけ
  - [ ] OLA が `pumice-core` の単体テストで検証できる
- **依存**: なし

## REQ-PUM-016: リアルタイム安全性と CPU 予算

- **優先度**: Must
- **ステータス**: Draft
- **説明**: `process()` の中で確保・ロック・IO・panic をしない。
- **予算**: 533 µs、目標 250 µs（512 サンプル / 48 kHz）。
- **見積り**: `NORMAL` ステレオで **50〜80 µs**。順逆変換が 2ch ぶんと、
  ビンごとのフォロワが 2 本。**フォロワは hop ごとにしか回らない**ので、
  サンプルレートで回るバンドパス列より安い（Velour の `Spectrum` 48 バンド ×
  2 本が 45 µs）。
- **スペクトル表示がタダ。** 音声パスに STFT があるので、`nxe_dsp::Spectrum` を
  別に回す必要がない。**表示しているスペクトルと処理しているスペクトルが
  同じ物**になる。
- **受入条件**:
  - [ ] criterion で `HIGH` / 512 サンプル / 48 kHz が 533 µs 以内
  - [ ] 極端値で非有限値を出さず panic しない
  - [ ] 非有限のサンプル 1 個でフォロワがラッチしない
  - [ ] 音声スレッドの経路に確保が無い（`assert_process_allocs`）
- **依存**: REQ-PUM-007, REQ-PUM-008

## REQ-PUM-017: サンプルレート・ブロックサイズ非依存

- **優先度**: Must
- **ステータス**: Draft
- **説明**: 同じ設定がどのレートでも同じ音になる。

- **`N` はレートに追従する**（`REQ-PUM-008`）。固定サンプル数だと 96 kHz で
  ビン幅が倍になり、`SHARPNESS` の意味が変わる。
- **時定数はすべて秒。** `SPEED` も WHERE の学習時定数も。
- **ブロックサイズ非依存は OLA が持つ。** リングバッファが hop 境界を管理する
  ので、ホストが何サンプル渡してきても出力は同じ。**これは `pumice-core` の
  テストで検証できる**（`REQ-PUM-015` の帰結）。
- **受入条件**:
  - [ ] 44.1 / 48 / 96 / 192 kHz でビン幅が目標の ±10% 以内
  - [ ] ブロックサイズ 1 / 64 / 512 / 4096 の出力が一致する
  - [ ] レート変更で係数が発散しない
  - [ ] レート変更が `process()` の外でだけ起きる
- **依存**: REQ-PUM-008

## REQ-PUM-019: DELTA

- **優先度**: Must
- **ステータス**: Draft
- **説明**: **削っている物だけを聴く。** `wet − dry` を出す。

- **パラメータにする**（UI だけのトグルにしない）。Sparkleur が per-band solo を
  パラメータにしている前例があり、オートメーションできると比較が楽。
- **`DELTA` は `MIX` と `OUTPUT` の前。** 削っている物そのものを聴きたいので、
  `MIX` で薄まっては用をなさない。
- **これが無いと `SHARPNESS` が調整できない。** 何を捕まえているかが
  聴けないと、参照の幅は勘で決めることになる。
- **受入条件**:
  - [ ] `DELTA` = on で、出力 + 通常出力が元の wet と一致する
  - [ ] `DEPTH` = 0 のとき `DELTA` の出力が無音（−120 dB 以下）
  - [ ] `DELTA` の on/off で不連続が出ない
- **依存**: REQ-PUM-001

## REQ-PUM-020: 速いディエッサではない

- **優先度**: Won't (v1)
- **ステータス**: Decided
- **説明**: **専用のディエッサ機構を持たない。時間分解能に床がある。**

| | `NORMAL` / 48 kHz |
|---|---|
| ゲインの更新間隔 | hop = **10.7 ms** |
| ゲイン変化の滲み | 窓 = **±21.3 ms** |

- **これより速い動きは原理的に作れない。** 5 ms のクリック的なキツさは
  捕まえられない。**書いておかないと、後で「効きが弱い」という誤った診断が
  出る**（`REQ-GLU-019` が同じ理由で書かれている）。
- **歯擦音そのものは射程内。** 「s」は 60〜150 ms で、周波数はほぼ一定・
  時間的には断続 — `REQ-PUM-003` の WHERE × WHEN がそのまま当たる形。
  **一般機構から落ちてくるものとして扱い、専用のノブを置かない**
  （`protect.rs` の判断と同型 — 既に動いている一つ目の隣に、歩調を合わせ
  続ける二つ目を置かない）。
- **もっと削りたい / 守りたいときはノードを置く。** 7 kHz にノードを置いて
  `depth` を上げるのが「もっと削る」、下げるのが「守る」。

## REQ-PUM-022: サイドチェイン参照

- **優先度**: Won't (v1)
- **ステータス**: Decided
- **説明**: 外部入力を参照にして「そこと被る帯域を削る」をやらない。
- **v1 に入れない理由**:
  - **aux 入力はこのリポジトリで前例が無い**（`REQ-GLU-020` と同じ）。

## REQ-PUM-023: 最大削減量の上限

- **依存**: REQ-PUM-002, REQ-PUM-004

## REQ-PUM-025: THRESHOLD

- **優先度**: Must
- **ステータス**: Draft
- **説明**: **どれだけ突出したら反応するか。** 0〜12 dB、既定 4.5。

- **内部定数だった。それが穴だった**（`PUM-10c`）。「どれだけ反応しやすいか」
  はこのプラグインについて人が最初に訊く問いで、答える場所が無かった。
- **既定は測った値** — 白色ノイズと歌の倍音がどちらもちょうど 0 dB を読む
  （`REQ-PUM-003`）。だが**合成素材での測定は出発点であって、どの声にも
  当てはまる答えではない**。
- **下げると反応しやすくなる。** `DEPTH` の隣で向きが逆になるが、しきい値は
  そういうものとして読まれる。
- **適応検出を落とした代役**（`REQ-PUM-003`）。**機構が自分で見つけていた
  はずの数を人に探させるので、明確に劣った答え**。それが機構が成立しなかった
  ことの代償で、隠さず書いておく。
- **受入条件**:
  - [x] 既定で広帯域ノイズの RMS 変化が 0.1 dB 未満
  - [x] 上げると歌の倍音への削減が浅くなる
  - [ ] 範囲 0〜12 dB が実素材で足りるか（`PUM-11`）
- **依存**: REQ-PUM-003

## REQ-PUM-024: プリセットを持たない

- **優先度**: Should
- **ステータス**: Draft
- **説明**: プリセットブラウザを持たない。**`DEPTH` 1 本がその役。**
- Doubler / Velour / Sparkleur / Air / Diorama と同じ判断。
- **帰結として既定値が製品の顔になる。** ノード 0 本のボーカルトラックに
  挿して `DEPTH` を回すだけで共鳴が引くことが最終の受入条件（`PUM-11`）。
