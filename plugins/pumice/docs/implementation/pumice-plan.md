# Pumice — 実装計画

> 最終更新: 2026-09-01

要件は [`../requirements/REQ-PUM.md`](../requirements/REQ-PUM.md)。
DSP 仕様は [`../specifications/dsp.md`](../specifications/dsp.md)、
UI 仕様は [`../specifications/ui.md`](../specifications/ui.md)。

**まだ 1 行も実装されていない。** 着手は `PUM-1`。

**単位ごとに「完了条件」を満たしてからコミットする。** 完了条件は「動いた」
ではなく**測れること**で書く。

## 順序の考え方

```text
PUM-1  空のラッパで PDC を通す        ← ゲート。**人が 4 ホストを開く**
PUM-2  OLA バッファと窓
PUM-3  参照とゲイン計算（STATIC）     ← ここで音が出る
PUM-4  適応 WHERE と MODE             ← 2 つ目のゲート
PUM-5  ノード曲線
PUM-6  dry / MIX / OUTPUT / DELTA
PUM-7  レート・ブロックサイズ非依存
PUM-8  CPU 予算
PUM-9  解析の受け渡し
──────── ここでパラメータ集合が凍る ────────
UI-22  NodeField（gallery で単体検証）
PUM-10 窓
PUM-11 既定値と耳                     ← **人が要る**
```

**ゲートが 2 つある。** ラインで初めて。

**`PUM-1` が 1 番目**なのは `roadmap.md` の基準 0 そのもの
（前提が崩れると後続が無駄になるものを先に）。**PDC が 4 ホストで効かなければ、
FFT 方式ごと選び直す**ことになり、`PUM-2` 以降が全部無駄になる。
`DBL-2` と同じ扱いで、**空に近いラッパのうちに人の手で確かめる**。

**`PUM-1` は DSP を 1 行も持たない。** レイテンシを申告して、
`nxe_audio::DelayLine` でその分だけ遅らせるだけ。**PDC が効いていれば
トラックはずれない** — 自分自身が試験になっている。

**`PUM-4` が 2 つ目のゲート**（`REQ-PUM-003`）。崩れたら「倍音を削らずに
共鳴だけ削る」が成立せず、製品が soothe の劣化版に縮む。`PUM-3`（`STATIC`）が
先にあるので、**比較対象がある状態でゲートを測れる**のが利点 —
受入条件が「`ADAPTIVE` の削減量が `STATIC` より 6 dB 以上小さい」なので、
`STATIC` が無いと測りようがない。

**`PUM-3`（ラッパで音が出る）が `PUM-4` より前。** `VEL-5` / `AIR-4` /
`DIO-4` と同じ判断。`SHARPNESS` も `SPEED` も効いたかの判断が耳寄りなので、
ホストの既定パラメータ UI で音が出る状態を先に作る。

**`UI-22` が `PUM-9` の後。** `roadmap.md` の基準 1（パラメータ集合が固まる
まで UI に投資しない）。`NodeField` は**このリポジトリで一番大きい UI 投資**
なので、一番作り直したくない。

## 共有クレートに上げるもの

**無い。** `REQ-PUM-015` のとおり、OLA バッファは `pumice-core` に置く。

| 何 | どこ | なぜ上げないか |
|---|---|---|
| OLA バッファと窓 | `pumice-core` | **1 個目の客しか居ない**（`architecture.md`）。ただし**パラメータ構造体を知らない自立したモジュールとして書く**ので、2 個目が来たら移動はファイルの移動だけで済む（`REQ-VEL-015` と同じ） |
| 前置和の区間平均 | `pumice-core` | 同上。3 箇所で使うが全部この製品の中 |

**`nih_plug::util::stft::StftHelper` は使わない**（`REQ-PUM-015`）。理由は
ライセンスと AU の道。**答え合わせの相手としては使う。**

## 新しい依存

| | ライセンス | どこに |
|---|---|---|
| `realfft` | MIT | `pumice-core` |

`realfft` は `rustfft`（MIT OR Apache-2.0）の実数入力ラッパ。**どちらも

### PUM-1 — 空のラッパで PDC を通す（**ゲート**）

`pumice` / `pumice-core` の 2 クレートを作り、ワークスペースと
`bundler.toml` に登録する。

**`pumice-core` は空ではなくなった。** 当初「`lib.rs` だけ」と書いていたが、
ラッパがレイテンシを申告するには **N が要る**。N の決め方は変換の性質で
あってラッパの都合ではないので、`.agents/rules/rust.md`（ラッパに DSP を
置かない）に従って `pumice_core::quality` に置いた。DSP はまだ 1 行も無い。

ラッパがやること:

- `AUDIO_IO_LAYOUTS` に 2→2 と 1→1（`REQ-PUM-011`）
- `initialize()` で `set_latency_samples(N)`
- `process()` で `nxe_audio::DelayLine` を通してその分だけ遅らせる
- パラメータは `QUALITY` **1 つだけ**（`.non_automatable()`）。
  申告値が動くことをここで試す

**UI は持たない。** ホストの既定パラメータ UI で足りる。

- **完了条件**:
  - [x] `cargo xtask bundle pumice --release` が通る
  - [x] `mise run check` が通る（**610 本**、うち Pumice が 9 本）
  - [x] 申告値と実際の遅れがサンプル単位で一致する
        （`the_delay_matches_what_is_reported`、4 レート × 3 段）
  - [x] **Ableton Live（VST3）と Studio One Pro（CLAP）で位相が合う**
        — 反転して無音（2026-09-01）
  - [x] **再生中に `QUALITY` を変えて音が復帰する**（2026-09-01）
  - [ ] Bitwig と Reaper（**方式の判断には影響しない**。`PUM-2` 以降と並行）

**方式の前提は抜けた**（2026-09-01）。**CLAP と VST3 が両方**通ったのが
大きい — フォーマットごとに PDC の伝え方が違うので、片方だけでは
「たまたま動いた」を排除できなかった。**FFT で進めてよい。**

残り 2 ホストは**方式の判断には影響しない**。Bitwig と Reaper はどちらも
PDC を持つホストで、ここで落ちるならホスト固有の問題であって
`REQ-PUM-007` の前提の問題ではない。`PUM-2` 以降と並行して確かめる。

**`QUALITY` の実行時切り替えも通った。** `.non_automatable()` にしたうえで
ブロック境界でだけ `set_latency_samples` を呼ぶ形が、少なくとも 2 ホストで
成立する。`REQ-PUM-008` の「停止中にだけ変えられる」という退避案は要らない。

**この単位で仕様の誤りが 1 つ見つかった。** 申告レイテンシを `N − hop` と
書いていたが、正しくは `N`（`quality.rs` の `latency` に理由がある）。
**PDC の検証は無効にならない** — このビルドは申告した値だけ遅らせるので、
値が何であれ位相は合う。

確かめ方: 同じ素材のトラックを 2 本並べ、片方にだけ Pumice を挿す。
**PDC が効いていれば位相が合ったまま**（この版は音を変えないので、
片方の位相を反転すると無音になる）。
- **依存**: なし
- **これが駄目だったら**: `REQ-PUM-007` に戻る。`QUALITY` を殺して
  レイテンシを固定にするのが第一手、それでも駄目なら**減算型
  バンドパスバンク**（レイテンシ 0）へ方式ごと戻す。その設計は
  `REQ-GLU-003` に既にある。

### PUM-2 — OLA バッファと窓

`pumice-core` に `stft.rs`。**`pumice` クレートは触らない。**

- リングバッファ、Hann、hop = N/4、`2/3` の正規化
- `N` をレートと `QUALITY` から決める（`dsp.md` の表）
- **確保は最大 N = 16384 で 1 回**

- **完了条件**:
  - [x] 全ビンのゲインが 1 のとき、再構成誤差が **−120 dB 以下**
        （3 レート × 3 段で実測）
  - [x] **ブロックサイズ 1 / 64 / 512 / 4096 の出力が一致する**
  - [x] `dsp.md` の N の表が 4 レート × 3 段で一致する（テストで固定）
  - [x] 音声パスに確保が無い
  - [x] 申告レイテンシ `N` と実際の遅れが一致（インパルス応答）

**踏んだ罠が 1 つ**: **`realfft` の `process()` は毎回確保する**
（内部で `make_scratch_vec` を呼ぶ）。使えるのは `process_with_scratch` だけで、
名前からは分からない。debug ビルドなら `assert_process_allocs` が捕まえるが、
気づかずに release で出荷すると誰も気づかない類の穴。

**`QUALITY` の 3 段はすべて `Stft::new` で計画する。** FFT の planning は確保
するので、切り替えのたびに計画すると音声スレッドで確保することになる。
3 つの計画・3 つの窓・いずれにも足りる 1 本の scratch を最初に作り、
切り替えは添字になる。

**`StftHelper` との突き合わせは完了条件から外した。** `pumice-core` の
dev-dependency に `nih_plug` を足すことになり、テスト 1 本のために
`vst3-sys` を dev グラフへ引き込む。**再構成誤差とブロックサイズ非依存は
直接測れる**ので、間接的な突き合わせで得るものが無い。
- **依存**: PUM-1

### PUM-3 — 参照とゲイン計算（`STATIC`）＋ ラッパ

`pumice-core` に `reference.rs` と `gain.rs`。**ここで音が出る。**

- 前置和の区間平均（参照 / ゲイン平滑の両方が使う）
- `e[k]`、`WHEN`、`THRESHOLD` / `SLOPE` / `CEILING`
- 最終ゲイン曲線の 1/12 オクターブ平滑
- ラッパに `DEPTH` / `SHARPNESS` / `SPEED` を足す

- **完了条件**:
  - [x] `DEPTH` = 0 で全ビンのゲインがちょうど 1（出力が入力と −120 dB 以下）
  - [x] **広帯域ノイズで削減量が 1 dB 未満**（`SPK-18` の再発防止）
  - [x] 削減量が入力ゲイン ±12 dB で **0.2 dB 以内**
  - [x] 共鳴が引き、`DEPTH` で単調に深くなる
  - [x] ブロックサイズ非依存、極端値で非有限値なし、3 段とも動く
  - [ ] **ホストで聴いて、共鳴が引くことを確かめる**（`mise run install pumice`）

**`SHARPNESS` の単調性はここでは測っていない。** 「広い盛り上がりへの削減が
単調に減る」は `reference` 層の性質で、`smoothing.rs` の
`a_spike_is_diluted_by_the_window` が幅の効果そのものを押さえている。
**エンジン全体での掃引は `PUM-11` で耳と一緒に**。

**テストで見つけた自分の誤りが 2 つ**、どちらもテスト側:

1. `Prefix` の精度テストが**希釈を精度と取り違えていた**。139 ビン幅の窓は
   1000 分の 1 を 700 万分の 1 に薄める。これは `f32` の分解能より下で、
   累算器が何であっても再現しない。**正しい実装で落ちるテストだった。**
   幅 0（窓が 1 ビン）で「差が厳密に元の値」を測る形に置き換えた
2. 動作範囲の「段が無い」テストが、**ビン間隔が提供できない滑らかさを
   要求していた**。100 Hz の半オクターブは 71〜141 Hz で、48 kHz / 2048 点
   では 3 ビンしかない。ランプはそれを標本化するビンより滑らかにはならない。
   「1 度上がって 1 度下がる」＋「ビンが解像する範囲では滑らか」に変えた
- **依存**: PUM-2

### PUM-4 — 適応 WHERE と `MODE`（**ゲート**）

`engine.rs` の中に入れた。**`adaptive.rs` は起こさなかった** — 長期フォロワは
`gain::Follower` の対称版で、専用の型を作ると `protect.rs` が警告している
「既に動いている一つ目の隣に、歩調を合わせ続ける二つ目」になる。

- `WHERE` = `e[k]` の長期フォロワ（hop 刻み、τ_w = 6 秒）
- `min(WHEN, WHERE)`
- `MODE` を core と wrapper の両方に

- **完了条件**:
  - [x] **掃引鋸波で `ADAPTIVE` の最大削減量が 0.5 dB 以下**（実測 0.29）、
        **かつ同じ素材で `STATIC` が 2.0 dB 以上削る**（実測 2.2〜4.5）
  - [x] **固定共鳴を足した同じ素材で、`ADAPTIVE` がその周波数を `STATIC` と
        同等以上に削り、倍音しか無い対照周波数より 1.5 dB 以上深い**
  - [x] `MODE` の切り替えで段が増えない（切り替えない実行との比較）
  - [x] 無音から立ち上げたとき `WHERE` が発散しない
  - [ ] **ホストで聴く**（`ADAPTIVE` と `STATIC` の差が分かるか）

**要件の受入条件を測って書き直した。** 「`STATIC` より 6 dB 以上小さい」は
**満たせない条件**だった — 正しい答えが「まったく削らない」なので、ゼロより
6 dB 小さい値は存在しない。両側の絶対値で書く形に直した（`REQ-PUM-003`）。

**仕様から 1 つ落とした。** WHERE の周波数平滑（1/6 オクターブ）は、
**WHERE が見つけるべきものを消していた**。2.5 kHz で 14 ビン幅の dB 算術平均は
20 dB の突出を 1.4 dB にする。`ADAPTIVE` が定常共鳴を **0.00 dB** しか
削らない状態だった（`STATIC` は 2.19）。保険が守ろうとしていた相手——
一定音程の持続——は `τ_w` と `MODE` が受け持つ。

**テストで自分の誤りをもう 2 つ捕まえた**（どちらもテスト側）:

1. 削減量を**出力 RMS の変化**で測っていた。基音は誰も触らないので RMS が
   支配され、**「まったく何もしない」と「4.5 dB 引く」の差が 1.5 dB に
   圧縮されていた**。エンジンが実際に掛けている削減カーブを見る形にした
2. 「切り替えで段が出ない」を**絶対値**で測っていた。ノイズは何もしなくても
   +1 から −1 へ隣り合う。切り替えない実行との比較に変えた
- **依存**: PUM-3
- **これが駄目だったら**: `REQ-PUM-003` に戻る。`min` を積や重み付き和に
  替えるのが第一手。**それでも倍音が削れるなら `ADAPTIVE` を落とし、
  製品は `STATIC` だけになる** — そのとき Pumice は soothe の再実装であって
  「ボーカルの soothe」ではなくなるので、**要件から書き直す**。

### PUM-4b — 「効きが弱い」を測った

**実機で聴いた感想から生えた単位**（`DIO-14` と同じ形）。2026-09-01、
`DEPTH` を回しても効きが弱いという感想に対して、**dB がどこで消えているかを
測った**。18 dB / Q=8 の共鳴が **3.4 dB の削減**にしかなっていなかった。

```text
18 dB の共鳴 → e 14.8 → WHEN 7.3 → ×0.7 = 5.1 → 平滑 → 3.4 dB
              参照汚染      dB平均      slope      1/12 oct
```

見つかったのは 4 つ。**どれも仕様の側の誤りで、実装の誤りではない。**

| | 何 | 効果 |
|---|---|---|
| 1 | **参照が自分の判定対象を含んでいた**（`SPK-18` と同型）。しかも `SHARPNESS` を狭くするほど悪化していた — 狭い窓ほど共鳴自身に埋め尽くされる | 3.4 → **8.9 dB** |
| 2 | **1 ビンのパワーは標準偏差 5.6 dB で揺れる。** その揺れが超過に見え、非対称フォロワが整流していた | ノイズ p95 4.06 → **2.59**、削減 11.5 → **13.1** |
| 3 | **地図が無音区間も平均していた。** duty 50% で削減が 6.34 → 3.69 dB に落ちていた | duty 50% で **5.80 dB** |
| 4 | **`SLOPE` 0.7 が `DEPTH` の内側にもう一段上限を作っていた** | 1.0 |

**`THRESHOLD` を 0 から 4.5 dB に上げた。** 0 は「普通の素材は近傍と同じ
パワーを読む」という前提で置いていたが、**読まない** — 白色ノイズが最悪
5.0 / 平均 1.0 dB、歌の倍音が最悪 5.3 dB を読む。`SPK-18` の手順どおり
測って、その上に置いた。

結果、**同じ 18 dB の共鳴への削減は 3.4 → 7.8〜8.6 dB（2.4 倍）**で、
同時に**普通の素材への削減は 0.71 → 0.00 dB**。効きと選択性が同時に上がった。

**2 度目の感想は「削りすぎまではいかない」**、つまり**上端が足りない**。
`SLOPE` を 1.0 → **2.0** に上げた。しきい値が普通の素材を守っていて、
傾きはその**上**しか触らないので、**両者は直交している** — 測ると傾き 1〜3 で
ノイズは 0.01 dB しか動かない。

| `SLOPE` | ノイズ | 歌（最悪） | 18 dB 共鳴 Q4 / Q8 |
|---|---|---|---|
| 1.0 | −0.00 | −0.80 | −7.8 / −8.6 |
| **2.0** | **−0.01** | **−1.59** | **−15.6 / −17.1** |
| 3.0 | −0.01 | −2.39 | 2 つが `CEILING` に張り付く |

**3.0 は駄目**。つまみの上端が上限に当たって何もしなくなる。2.0 なら
`DEPTH` 半分が従来の音で、上半分が引き返す領域になる。

**3 度目の感想は「`ADAPTIVE` だとエフェクトがかかっている気がしない。
`STATIC` の 40〜50 なら有用そう」。** 地図が立ち上がっていなかった。
原因は 2 つ、どちらも**実装ではなく設計の見落とし**。

**1. ゼロから始まる指数平均のバイアス。** `n` 回更新した状態は真の平均の
`1 − (1−c)^n` 倍しかない。τ_w = 6 秒だと:

| | 1s | 2s | 3s | 5s | 8s | 20s |
|---|---|---|---|---|---|---|
| 補正前・連続 | 0.00 | 0.00 | −1.24 | −5.58 | −10.11 | −15.66 |
| 補正前・休符あり | 0.00 | 0.00 | 0.00 | −1.83 | −2.78 | −10.66 |
| **補正後・連続** | **−17.43** | −17.12 | −16.89 | −16.74 | −16.90 | −16.57 |

**挿してフレーズを再生しても、最初の 3〜5 秒は完全に無反応だった。**

**2. `reset()` が地図を消していた。** ホストは停止・ループ・再生位置の移動
ごとに `reset()` を呼ぶ。**フレーズを繰り返し試聴するという実際の作業手順で
は、地図が永久に形成されない。** 変換のリングと短期フォロワは信号についての
状態なので消すが、**地図は素材についての知識**で、消してはいけなかった。

**測る指標を 1 回間違えた。** 「最初の数秒で倍音を削っていないか」を
**全時刻・全ビンの最悪の瞬間値**で測り、18 dB を読んで失敗させ、
ウォームアップを 4 秒まで伸ばして共鳴への効きを 4 秒待ちにしていた。
**耳が聞くのは出力の変化**で、そちらは終始 **0.34 dB** だった。
瞬間の最悪値は可聴性の代理にならない。

- **完了条件**:
  - [x] 平坦なノイズの RMS 変化が **0.1 dB 未満**（従来 1.0 dB）
  - [x] 歌の倍音への削減が `DEPTH` 全開でも最悪 **2.0 dB 以下**、
        平均 **0.1 dB 以下**
  - [x] 同じ素材で `STATIC` が **10 dB 以上**削る（素材が効くことの確認）
  - [x] **`DEPTH` 全開が「削りすぎ」に届く**（18 dB の共鳴から 15.6〜17.1 dB）
  - [x] **`ADAPTIVE` が 1 秒で全力に達する**（従来 8〜20 秒）

### PUM-5 — ノード曲線

`pumice-core` に `nodes.rs`、ラッパに **26 個**のパラメータ
（6 × 4 + 動作範囲の 2 つ）。

- 対数周波数上のガウシアン、`width` は半値全幅
- `weight = 動作範囲 × clamp(1 + Σ depth·bump, 0, 2)`
- **動作範囲を `Settings` から `Controls` に移した。** 端の位置は操作対象で、
  端の**柔らかさ**（レイズドコサイン 1/2 オクターブ）だけが定数
- **パラメータが動いたときだけ組み直す**（6 ノード × 最大 8193 ビン）

**ラッパは `#[nested(array, group = "Nodes")]`。** `on_1`〜`d_6` という id が
自動で付き、ホストがノードごとにまとめて表示する。24 個のフィールドを
手で並べるより、1 つの構造体を 6 つ持つほうが**id を取り違えない**。

**ノードのパラメータにスムーザを付けない。** 毎ブロック読んで「前回組んだ
重みと違うか」を比べる作りなので、スムーザがあると毎ブロックが変化になって
無駄に組み直す。曲線の段は変換のオーバーラップが元々クロスフェードする。

- **完了条件**:
  - [x] `enabled` が全部 off で重みが**厳密に** 1
  - [x] `depth` < 0 のノードがその周波数の削減を**止める**（実測 −0.5 dB 未満）
  - [x] `freq` を掃引して段差が出ない（1% 刻みで重みの変化 0.1 未満）
  - [x] `DEPTH` = 0 なら、どのノード設定でも出力が **−120 dB 以下**で一致
  - [x] 重なったノードが加算され、`0..=2` で頭打ちになる
  - [x] `width` が半値全幅になっている（4 つの幅で検証）
- **依存**: PUM-4

### PUM-6 — dry / `MIX` / `OUTPUT` / `DELTA`

- `nxe_audio::DelayLine` を `N`（`PUM-1` のものを本番に昇格）
- `DELTA` は `MIX` の前

**dry の取り出しは 256 サンプルの固定チャンクで回す。** ホストが渡す
バッファは変換に**その場で上書きされる**ので、dry は先に取っておいて後から
読み戻す必要があり、読み戻す位置はバッファ内のどこに居たかで変わる。
固定チャンクにすれば**ホストに最大バッファ長を聞かずにディレイラインの長さが
決まる**。変換は何を渡されてもサンプル単位で同じ（`REQ-PUM-017`）なので、
チャンクに割っても出力は変わらない。

- **完了条件**:
  - [x] `MIX` = 0 で遅延入力との差が **−120 dB 以下**
  - [x] `DEPTH` = 0 で遅延入力との差が **−120 dB 以下**（`PUM-3` から継続）
  - [x] dry の遅延が申告値と**サンプル単位で一致**（3 段ともインパルスで）
  - [x] `DELTA` の出力 + `MIX`=0 の出力 = 元の wet（−110 dB 以下）
  - [x] `DEPTH` = 0 のとき `DELTA` が無音（−120 dB 以下）
  - [x] `OUTPUT` が 0 dB で厳密に unity、0.5 倍が厳密に半分
  - [x] `MIX` を掃引しても段が増えない（掃引しない実行との比較）
- **依存**: PUM-5
