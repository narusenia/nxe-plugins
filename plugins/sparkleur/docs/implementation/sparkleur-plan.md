# Sparkleur — 実装計画

> 最終更新: 2026-08-26

要件は [`../requirements/REQ-SPK.md`](../requirements/REQ-SPK.md)、
DSP 仕様は [`../specifications/dsp.md`](../specifications/dsp.md)、
UI 仕様は [`../specifications/ui.md`](../specifications/ui.md)。

**単位ごとに「完了条件」を満たしてからコミットする。** 完了条件は
「動いた」ではなく**測れること**で書く。Doubler と Velour で 3 回学んだ順序が
あるので、それを踏む。

## 順序の考え方

**Velour で 4 回起きたことをここでも見込む**: 実測が仕様の数字を否定する。
だから「測れる土台」を先に作り、耳の判断を最後にまとめる。

```text
SPK-1  共有クレート ✅     ← ここが通らないと何も書けない
SPK-2  クロスオーバー ✅   ← 平坦性が全部の前提（ゲート）
SPK-3  検波と時定数 ✅
SPK-4  ゲイン計算（上下）✅ ← 製品の核
SPK-5  CHARACTER ✅
SPK-6  Sparkle ✅
SPK-7  De-Harsh / Sub Protect ✅
SPK-8  ラッパとパラメータ ✅ ← ここで初めて音が出る
SPK-9  詰め（レート・ブロック・極端値）✅
SPK-10 nxe-ui の delta 符号付き化 ✅
SPK-11 param_bind の共通化 ✅
SPK-12 UI マクロ層 ✅
SPK-13 UI Band Field ✅
SPK-14 UI 小窓とメーター ✅
SPK-15 UI Advanced
SPK-16 解析の配線 ✅
SPK-17 CPU 予算 ✅
SPK-18 既定値と耳
```

**`SPK-2` がゲート。** 分割の和が平坦でなければ「全部 0 で何もしない」が成立
せず、その上の全部が意味を持たない。Velour の `VEL-1`（カーブのレベル正規化）と
同じ位置。

### SPK-1 — 共有クレート `nxe-audio` ✅

`velour-core` から `shaper` / `oversample` / `biquad` / `envelope` / `guard` を
新クレート `crates/nxe-audio` に移す。`guard` は一般化する。

- **完了条件**:
  - [x] `nxe-audio` が nih-plug / Vizia / `velour-core` に依存しない
  - [x] **Velour のテストが 1 本も落ちない**（241 本が 241 本のまま通り、
        `N = 1` の形を固定する 1 本を足して **242 本**）
  - [x] `RelativeGuard` が帯域・参照帯・しきい値を引数で受ける
  - [x] Velour 側が「Harsh と Sib を 2 個作る薄いラッパ」になり、既存の
        `guard::tests` がそのまま回帰テストとして残る（信号で駆動する 7 本は
        そのまま。純関数の 2 本は `gain_of` と一緒に `nxe-audio` へ）
  - [x] `velour-core` に残るのは `bands` / `texture` / `density` / `engine` と、
        Velour のチューニングだけになった `envelope` / `guard`
- **要件**: REQ-SPK-015
- **依存**: なし
- **決めたこと**: `nxe-dsp` には入れない。あちらは「音を変えない」ことが
  doc に書かれた契約で、**解析はバグっても絵が壊れるだけ、処理はバグると音が
  壊れる**（リスクの階級が違う）
- **決めたこと**: `density` は移さない。Sparkleur のコンプは上下マルチバンドで
  別物。**要求されるまで上げない**（`architecture.md`）
- **決めたこと**: `RelativeGuard<N>` は**参照フォロワを 1 本だけ持ち、帯域を
  N 本持つ**。「Velour が 2 個作る」だと同じ信号に同じ帯域通過を 2 回かけて
  同じ答えを得ることになる。`VEL-16` の内訳が示すとおり、この構造で効くのは
  フィルタの本数
- **決めたこと**: 設定は `Settings<N>`（参照帯・帯域としきい値・時定数・傾き・
  最大引き量）を**呼び出し側の `const` 1 個**で渡す。引数 5 本より、何を
  どこまで守るのかが 1 ブロックで読める
- **決めたこと**: 互換の再輸出を置かない。`velour` も `nxe-audio` を直接引く。
  例外は測定ヘルパの `harmonics` 1 つだけ（下）
- **踏んだ罠**: **`harmonics` も一緒に移すことになった。** 移す 5
  モジュールのテストが全部これで書かれていて、`nxe-audio` は `velour-core` に
  依存できない（向きが逆）。計画では「`velour-core` に残る」と書いていたが、
  残すと移動先のテストが 1 本も書けない。移して `velour_core` が再輸出する形に
  した — `crate::harmonics::tone` と書いてある既存のテストが無修正で通る
- **踏んだ罠**: **`envelope` は「ファイルの移動だけ」では済まなかった。**
  attack 5 ms / release 150 ms と `REFERENCE_DB` −18 dB は**歌に対して耳で
  決めた数**で、Sparkleur は `SPEED` と帯域中心から導出する（`REQ-SPK-005`）。
  時定数を `Envelope::new` の引数に出し、Velour の 3 つの数は
  `velour_core::envelope`（`vocal()` と `REFERENCE_DB`）に残した。**共有部品が
  片方の製品の好みを黙って運ばないこと**が境界の引き方

### SPK-2 — クロスオーバー（ゲート）✅

`crossover.rs`。LR4 の木 + オールパス補正、5 帯域、`FOCUS`。
**`sparkleur-core` クレートもここで作った**（`VEL-1` と同じ位置）。

- **完了条件**:
  - [x] 全帯域 unity のとき、**20 Hz〜20 kHz の和の振幅が ±0.1 dB 以内**
  - [x] 各帯域が隣の帯域と 24 dB/oct で交差する（交差点で両側とも −6 dB、
        境界が 1 つだけ効く区間の裾が 24 dB/oct）
  - [x] `FOCUS` で 5 境界が**まとめて**動き、比が保たれる
  - [x] `FOCUS` を振り切っても最上端がナイキストを超えない
  - [x] 44.1 / 48 / 96 / 192 kHz で平坦性が保たれる
  - [x] 係数の再計算がブロック単位（サンプルごとに入っていない）
  - [x] hostile な `FOCUS` で非有限を出さない
- **要件**: REQ-SPK-001, REQ-SPK-002
- **依存**: SPK-1
- **決めたこと**: オールパスは `LP + HP` の和。専用に書かない — **それが実体
  そのもの**なので、分割と同じ係数から 2 つ目の導出を作らずに済む。コストは
  1 チャネル biquad 40 個で、専用オールパスなら 22 個。**`SPK-17` で予算が
  厳しければ最初に触るのはここ**（同じフィルタなので音は変わらない）
- **決めたこと**: `Crossover` は **1 チャネル分**。ステレオは 2 個持つ
  （フィルタとゲインはチャネルごと、検波だけリンク — `REQ-SPK-011`）
- **決めたこと**: 天井は 4 点全部に同じ式を当てる。**順序は守らせない** —
  `LP(f) + HP(f) = AP(f)` はコーナーの値に依らないので、境界が重なっても
  和の平坦性は落ちない（空の帯域が 1 つできるだけ）
- **踏んだ罠**: **帯域の裾は 24 dB/oct とは限らない。** 木構造なので各帯域は
  自分の境界だけでなく上流の全部のハイパスを通っている。band 5 の 6 kHz より
  1 オクターブ下は `HP(1500)` がまだ効いていて **30 dB/oct** で落ちる。
  24 dB/oct を測るなら境界が 1 つしか効かないところ（band 1 の 120 Hz より上、
  band 2 の 120 Hz より下）。最初に書いたテストはこれで落ちた — **フィルタは
  最初から正しく、間違っていたのは期待値**
- **踏んだ罠**: **帯域の幾何中心は 0 dB ではない。** band 2 は 120〜400 Hz で
  1.7 オクターブしかないので、中心の 220 Hz でも両側の 24 dB/oct の肩が
  −1.5 dB 持っていく。「帯域が自分の範囲を通す」テストの閾値をここで間違えた
- **決めたこと**: 「係数がブロック単位」は `#[cfg(test)]` の再構築カウンタで
  測る。**`split` を 1000 回呼んでカウンタが動かないこと**と、
  **`set_focus` に別の値を渡せば動くこと**を同じテストで見る（`VEL-10` の
  「測定が失敗できることを確かめる」）

### SPK-3 — 検波と時定数 ✅

`detector.rs`。帯域ごとのパワー追従、`SPEED` からの時定数、帯域からの床。

- **完了条件**:
  - [x] ~~一定の正弦で検波値がその振幅を読む（±0.5 dB）~~ **条件が間違っていた。**
        非対称な追従は平均に落ち着かないので、どんな基準を選んでも「読む」に
        ならない。代わりに測れる 2 つを固定した: **読み値が帯域の RMS と
        ピークパワーの間に入る**ことと、**素材が 1 dB 動けば読み値も 1 dB 動く**
        こと（±0.1 dB）。後者がゲイン計算が実際に要る性質
  - [x] `SPEED` 最速でも LOW の attack が**導出された床（33 ms）を下回らない**
  - [x] 弾道が 44.1 / 48 / 96 / 192 kHz で同じ
  - [x] 非有限のサンプル 1 個でラッチしない
  - [ ] `SPEED` 最速・50 Hz 正弦で **THD が上がらない**（波形変調していない）
        — **`SPK-4` に送る。** ここにはまだ掛けるゲインが無いので THD は
        定義できない。代わりに原因のほうを固定した（下のステップ応答）
- **要件**: REQ-SPK-004, REQ-SPK-005
- **依存**: SPK-2
- **決めたこと**: モノ和のために 3 本目の `Crossover` は作らない。**クロスオーバーは
  線形**なので、モノ和の帯域は両チャネルの帯域の平均と厳密に一致する。呼び出し側が
  既に持っているものを足すだけ
- **決めたこと**: 読み値は `10·log10(e)` = **RMS 基準**（仕様の式そのまま）。
  全振幅の正弦は −3.01 dB から始まる。`T_down` = −18 dB 等はこの目盛り
- **決めたこと**: 解決後の時定数を秒でも保持して公開する。**床がこの単位の
  全部**なので、何秒に落ち着いたかが読めないと確かめようがない
- **踏んだ罠**: **定常正弦は床の効果を測る道具として弱い。** 50 Hz では
  release の 20 ms が単独で読み値を持ち上げるので、attack が 1 ms でも 33 ms でも
  リプルは 1.0 dB 対 1.0 dB でほとんど変わらない。**「対照実験が差を出さない」と
  いう形の失敗**で、`VEL-10` の「測定が失敗できることを確かめる」行がそれを
  捕まえた。差が出るのは**ステップ応答** — 床のある帯域 1 は自分の中心の
  2 波長を切れず、床の届かない帯域 5 は 1 ms で追従する（**33 倍**）
- **踏んだ罠**: **非対称な追従は平均を読まない。** 実測で RMS の
  +0.05〜+2.54 dB の間に座り、位置は attack/release の比が決める（比 4 で
  +0.05〜0.9、比 20 で +2.5）。素直なコンプの挙動だが、**しきい値を計算で
  出せないということ**でもある — `SPK-18` で耳で決める理由がここにある

### SPK-4 — ゲイン計算（上下コンプ）✅

`dynamics.rs`。下げ・上げ・上限・床・ニー。**製品の核。**

- **完了条件**:
  - [x] `SPARK` = 0 で全帯域のゲインが**ちょうど 0 dB**
  - [x] 下げの比が設定どおり（入力 +12 dB に対する出力の傾きで測る）
  - [x] 上げの比が設定どおり
  - [x] 上げが `CEILING` を超えない、かつ**ちゃんと上限に到達する**
        （到達させるには床を開けるか CRUSH の比が要る — 下の「決めたこと」）
  - [x] **無音（+ ノイズフロア）でゲインが上がらない**（床が効いている）
  - [x] 床を開放すると上がる（`LIFT` が効いている）
  - [x] ニーが連続（しきい値の前後で微分が飛ばない）
  - [x] per-band の重みが線形にスケールする
  - [x] hostile な値で非有限を出さない
  - [x] **`SPK-3` からの持ち越し**: `SPEED` 最速・50 Hz で THD が上がらない
        （`tests/chain.rs`。0.26% 対 床なし 2.0%）
- **要件**: REQ-SPK-003, REQ-SPK-009
- **依存**: SPK-3
- **決めたこと**: 状態を持たない。`nxe_audio::guard::gain_of` と同じ理由で、
  **`SPARK` = 0 がちょうど 0 であること・どちらの側も反転しないこと・ニーに角が
  無いこと**は信号を流さずに測れるべき性質
- **決めたこと**: 下げと上げは**同じ関数の鏡像**。「しきい値からどちら向きに
  何 dB 出たか」を渡し分けるだけで、ニーの 2 次式も上限も 1 か所で済む
- **決めたこと**: 比が 1 未満はエキスパンダで別の製品なので、`max(1.0)` で
  留める。**hostile な比が反転ではなく無効化になる**
- **見つけたこと**: **既定の床では POLISH も GLOSS も上限に届かない。**
  実測で最大 4.0 dB（上限 6）と 8.0 dB（上限 9）。CRUSH（比 3.0 / 上限 15）
  だけが既定の床で上限に当たる。**聴き手が実際に当たっている制限が
  `CHARACTER` で入れ替わる**ということなので、完了条件の「ちゃんと上限に
  到達する」は床を開けるか CRUSH で測るのが正しい
- **踏んだ罠**: **有限の dB は有限のゲインではない。** hostile テストが
  `GAIN_i` = 1e9 dB を渡したとき、`band_gain_db` は有限を返すのに
  `linear()` が無限大を返した。**ここまでで最初の「実装側の」バグ**（`SPK-2`
  と `SPK-3` の 4 本はどれもテストの期待値が間違っていた）。`MAX_GAIN_DB`
  = ±48 dB で蓋をした — `CHARACTER` が届く 15 dB のはるか外側なので、
  趣味の制限ではなく算術の制限
- **決めたこと**: `GAIN_i` は `SPARK` の外側（`dsp.md` の式どおり）。
  **`SPARK` = 0 が振幅平坦なのは `GAIN_i` = 0 のときだけ**という帰結を
  文書に書いた。`GAIN` はダイナミクスではなく静的な EQ だから

### SPK-5 — CHARACTER ✅

`character.rs`。アンカー 3 点の補間。

- **完了条件**:
  - [x] 3 つのアンカー位置でちょうど表の値になる
  - [x] 端から端まで動かして不連続が無い（0.001 刻みで全 10 項目）
  - [x] 軸を動かしてもラウドネスが **±1.5 dB 以内**（トリムで吸収）
        — **実測 0.98 dB で、トリムは 0 のまま要らなかった**
  - [x] POLISH と CRUSH で倍音の偶奇比が **1.5 倍以上**違う
  - [x] hostile な位置で中央にフォールバックする
- **要件**: REQ-SPK-006, REQ-SPK-010
- **依存**: SPK-4, SPK-6
- **決めたこと**: レベルトリムの枠を**最初から置く**。Velour で `TEXTURE` が
  −3.0 dB 動いて後から吸収する必要が出た。比とニーを変えれば平均レベルは
  動くので、同じことが起きる。**実測 0.98 dB でまだ要らなかったが、枠だけ
  先にあることに意味がある** — 素材を変えれば動く
- **決めたこと**: **しきい値は軸に乗せない。** `T_down` / `T_up` は製品に
  1 組。しきい値が `CHARACTER` で動くと、軸が「何が起きているか」と
  「どれくらい起きているか」の両方を動かすことになり、`REQ-SPK-010` が
  分けたがっているものが混ざる。軸が運ぶのは**形**だけ
- **決めたこと**: 既定位置は 0.27（POLISH 寄り、`REQ-SPK-006`）
- **決めたこと**: `Sparkle` の偶奇テストは軸から `(β, h)` を引く。数字を
  テストに写すと**軸を直してもテストが通ってしまう**ので、軸そのものを
  測っている状態にする
- **決めたこと**: Velour の `texture.rs` と**同じコードにしない**（仕様どおり）。
  補間は同じ 3 点 2 区間だが、乗っている 10 項目が全部違う

### SPK-6 — Sparkle ✅

`sparkle.rs`。オーバーサンプル → シェイパ → HPF → トランジェントゲート。

- **完了条件**:
  - [x] `AIR` = 0 で生成層が**ちょうど無音**（早期 return。オーバーサンプルの
        ブロックごと走らせない）
  - [x] `SNAP` = 0 で静的、= 1 で持続音に対して光らずアタックで光る
        （無音 0.000 / アタック 1.000 / 持続音 0.008）
  - [x] 4x で最悪ケースの折り返しが **−60 dB 以下**（2 次の上蓋で足りた）
  - [x] 入力の上蓋が**ホストレート**基準（内部レートではない）
  - [x] `CHARACTER` で偶奇比が動き、**足す量は動かない**（正規化の帰結）
  - [x] 生成物が HPF より下に漏れない
- **要件**: REQ-SPK-007
- **依存**: SPK-2
- **踏むと分かっていた罠**（踏まずに済んだ）: Velour の `VEL-3` で AIR の入力に
  上蓋を付けるまで**どんなドライブでも −44 dB で折り返した**。上蓋を**内部
  レート**基準に書いて 1 回間違えたので、**ホストレート**基準で書いた。
  `Factor` を変えても上蓋が動かないことを同じテストで確かめている
- **踏んだ罠**: **非対称なフォロワを比の分子に置くと、持続音でゲートが
  半開きになる。** 仕様の fast は 1 ms / 40 ms で、`SPK-3` で分かったとおり
  非対称な追従は平均とピークの間に座る — 1:40 の fast は対称な slow より
  **どんな定常音でも約 3 dB 高い**。実測でゲートが 0.44 開いたままだった
  （`REQ-SPK-007` が禁じている挙動そのもの）。**フォロワを両方対称にして、
  40 ms のリリースを比の後ろのホールドに移した** — 連続する子音でバタつかせない
  という元の意図はホールドがそのまま引き受ける。**`SPK-3` の知見が 1 つ下の
  単位で直接効いた**形
- **決めたこと**: HPF は 6 kHz 固定ではなく**帯域の下端に追従**する。役目が
  「出てきた帯域より下に足さない」なので、`FOCUS` が動けば一緒に動くのが筋
- **決めたこと**: カーブのドライブは定数（仮 4.0）。仕様が値を書いていなかった
  が、`AIR` は出力ゲインを動かすと明記されている（`REQ-SPK-007`）ので
  ドライブは制御になりようがない。`SPK-18` の表に足した
- **見つけたこと**: 3 個目のパワーフォロワになった（`guard::Follower`、
  `Detector`、ここ）。共通化は積み残しに 1 行入れてある — **形が 3 つとも
  違う**（帯域通過込み / 配列 / 単体）ので、`SPK-6` の中で混ぜずに単位を分ける

---

### SPK-7 — De-Harsh / Sub Protect ✅

`protect.rs`。`nxe_audio::RelativeGuard` を 1 個 + `CEILING` の値違い。
**新しい機構を足さない。**

- **完了条件**:
  - [x] 入力ゲインを ±12 dB 変えても動作量が **0.2 dB 以内**
  - [x] 偏差を最小にすると De-Harsh がちょうど無効
  - [x] バランスの取れた素材では発火しない / 偏った素材では 3 dB 以上引く
  - [x] Sub Protect が LOW の上げ量だけを制限し、他の帯域を触らない
  - [x] `reduction_db` を公開する（`SPK-13` の図が描く）
- **要件**: REQ-SPK-008
- **依存**: SPK-4, SPK-5
- **決めたこと**: Sub Protect は `Weights` に `ceiling_scale` を 1 項目足す
  だけ。ゲイン計算は 1 本のまま。**「専用の処理を足さない」がコードの形に

  予算内なので、**CPU は理由にならない**。理由は「区画の背景に解像度は要らない」
  ほうだけ（`SPK-16`）
- **決めたこと**: 4x が既定のまま。**2x にしても 11 µs（10%）しか減らない** —
  Velour は生成器が 3 本あったので 4x が高くついたが、ここは Sparkle の 1 本
  だけ。**折り返しを 14 dB 買い直す理由が無い**
- **測ったこと**: `FOCUS` を毎ブロック動かしても **+2 µs**（1 チャネル 40 個の
  biquad を組み直している）。`CHARACTER` を毎ブロック動かすのは**測れない**
  （Sparkle のカーブ 1 本ぶんの正規化しかない。Velour は 3 本だった）
- **測ったこと**: **無音に落ちていく経路も 110 µs で、働いているときと同じ。**
  積み残しにあった「デノーマルの掃除」は**やる必要が無かった** —
  **nih-plug が `process` の前後で FTZ を x86 でも aarch64 でも有効にする**
  ので、ホストの中では 1 次フィルタの尾がデノーマルになりようがない。
  この機械（Apple Silicon）はデノーマルが速いので単独では答えにならないが、
  FTZ のほうが根拠として強い

## 見込んでいる罠（Velour で払った授業料）

前の 2 製品で時間を溶かした形が、そのまま来る場所が分かっている。

| 罠 | どこで来るか |
