# UI を開くと DAW が重くなる — 原因と対策

**2026-08-30〜31 の調査記録。解決済み。**

**原因は 2 つあった。別々の問題で、片方が症状のほぼ全部だった。**

| | 症状 | 原因 |
|---|---|---|
| **A** | **UI を一度開くと、消してもホストを再起動するまで、DAW の操作がポインタに追従せず滑るように遅れる** | `baseview` が**ホストのプロセス全体**でマウスイベントの合成を切っていた（1 行） |
| **B** | 窓が開いている間、ホストの UI スレッドの **62 %** を食う | 描画・レイアウト・バインディングの 7 つの無駄 |

**体感していたのは A。** B は本物のコストで直す価値もあったが、**A を直すまで症状は 1 ミリも変わらなかった。**

---

## A — マウス合成がホストごと切られていた

### 犯人

```rust
// baseview/src/macos/view.rs, updateTrackingAreas の中
let _: () = msg_send![class!(NSEvent), setMouseCoalescingEnabled: NO];
```

`setMouseCoalescingEnabled:` は **`NSEvent` のクラスメソッド**で、ビューでも
ウィンドウでもなく**プロセス全体**に効く。そして**誰も元に戻さない。**

macOS は通常、マウス移動イベントを合成（coalescing）してアプリのキューが冗長な
イベントで溢れないようにしている。これを切ると、ホストは**すべての移動イベントを
1 つ残らず**受け取る。プラグインの UI を一度開いた瞬間から、そのプロセスが
終わるまでずっと。

### 症状がこれで全部説明できる

| 観測 | この原因で |
|---|---|
| **マウスで動かすと**遅れる | 移動イベントが洪水になるのはその時だけ |
| 滑らかに遅れて追いつく | 間引かれない移動イベントを順に処理している |
| **プラグインを消しても直らない** | ビューでも窓でもなく**プロセスの設定**で、戻していない |
| **ホストを再起動すると直る** | 新しいプロセス |
| UI を一度も開かなければ起きない | `updateTrackingAreas` はビューが窓に入るとき呼ばれる |
| 他社 VST では起きない | 普通そんなことはしない |
| `sample` でホストが **97 % アイドル** | 撮影中にマウスを動かしていなければ、当然何も出ない |

### 直し方

**触らないようにしただけ**（`narusenia/baseview` `nxe-2026-08-31c`）。
`NSTrackingMouseMoved` のトラッキングエリアがあれば `mouseMoved:` はそのビューに
届く。合成は「**他の全員が**冗長なイベントを何個掻き分けるか」を決めているだけで、
プラグインが触っていいものではない。

**これは baseview を使う全プラグインに効くバグ**なので、上流に投げる価値がある。

### なぜ見つけるのに丸一日かかったか

**「重い」を CPU の話だと思い込んだから。** 最初に `sample` を撮ったら本当に
62 % 食っていたので、そこから B の修正が 7 つ出てきて、数字は 1/4 になった。
**でも症状は変わらなかった。**

決め手になったのは、CPU ではなく**「誰が何をしているか」を消していく**測り方:

| 測ったこと | 結果 |
|---|---|
| 遅い状態でホストを `sample` | **97 % アイドル。私たちのコードは 1 フレームも走っていない** |
| `WindowServer` を正常時と遅い時で `sample` | **区別がつかない**（busy 15 519 対 15 710）。合成側は無罪 |
| ディスプレイを 1 台に | 変わらない |
| **描画をホストの窓に出さないビルド** | **遅くなる。提示は無関係** |
| **OpenGL を一切作らないビルド** | **遅くなる。描画そのものが無関係** |

最後の 2 つで「描画ではない」が確定し、`open_parented` に残っている処理が
**ビューを窓に足すことだけ**になって、その中にこの 1 行があった。

**外した仮説は 6 つ**（下の「外した仮説」）。**忙しくないのに遅いなら、見るべきは
処理ではなく設定と待ち**、というのがこの調査の教訓。

## B — 窓が開いている間のコスト

**実測（Fender Studio Pro 8.0.3 / NXE Velour VST3 / Apple Silicon / Retina）。**
`sample` をホストに対して撮り、メインスレッドだけを見た:

| 状態 | main thread busy | うち `on_frame` |
|---|---|---|
| UI なし | 8 % | — |
| UI あり・無音 | 10 % | 1.1 % |
| **UI あり・実音声を再生** | **70 %** | **62.2 %** |

**無音だと 1.1 %。** 重いのは「窓が開いていること」ではなく「**値が変わり続ける
こと**」。

### なぜホストが遅くなるのか（構造）

`baseview` の macOS バックエンドは、窓を開いたスレッドのラン ループに
`CFRunLoopTimer` を刺す。プラグインにとってそれは**ホストのメインスレッド**で、
`on_frame` の中身は全部そこで同期実行される。**DAW の UI スレッドが奪われる。**

### 62 % の内訳（メインスレッド比）

| | |
|---|---|
| `femtovg::Canvas::flush` → `OpenGl::render` | **45.4 %** |
| `flushBuffer`（GL swap） | 9.0 % |
| `on_frame_update`（レイアウト + テキスト再シェイプ） | 7.4 % |
| パス構築 | 9.8 % |

**幾何の計算ではなく GL への送信が全部。** Apple Silicon の OpenGL は Metal
エミュレーションで、**draw call ごとにパイプライン状態を組み直す**。効くのは
「ピクセルを減らす」ではなく「**draw call を減らす**」。

### 直した 7 つ

**リポジトリ側:**

1. **読み値のレンズが毎フレーム走っていた。** `Ui::params.map(|_| ...)` の中で
   `Handoff` を読んでいた。`binding_system` はハートビートと無関係に**毎フレーム
   全ストアを評価する**ので、66.7 Hz で `String` を作り直し窓全体を描き直して
   いた。**ハートビートでモデルにコピーし、レンズはそのフィールドを見る**形に。
   Velour / Sparkleur の帯域図、Sparkleur の Advanced 表と伝達曲線も同じ形だった
2. **粒と反射の描画がアイテムごとに `fill_path` していた。** 同じ paint なので
   1 パスにまとめた

**vizia フォーク（`nxe-2026-08-31c`）:**

3. **見えない背景・枠・アウトラインを描いていた。** 透明でも幅ゼロでも、全 view に
   ついて。**456 → 219 draw call / フレーム**
4. **毎フレーム窓全体を描き直していた。** `draw_system` が全画面を `clear_rect`
   して全 entity を歩く。**1 フレームの draw call の 63 % がテキスト**で、その
   ほとんどが一度も変わらないラベルだった。変わった矩形だけ描くようにした
   （`Style::dirty_rect`）。**219 → 68**
5. **文字が変わるだけでツリー全体を再レイアウトしていた。** ビューが内容で
   サイズを決めているときだけにした。そのために `readout::cell` は幅も高さも固定
6. **入力の応答がタイマー待ちだった。** `on_event` でも描くようにし、1 フレーム
   より速くは描かないよう制限した

**baseview フォーク（`nxe-2026-08-31c`）:**

7. **フレーム タイマーが 66.7 Hz だった。** 60 Hz に。**30 Hz は駄目** — プラグイン
   の 30 Hz ハートビートとビートして、更新が 1 フレームに 2 回届いて 1 回しか
   描かれず、メーターがつっかえる。**タイマーはそれを養うものより速くなければ
   ならない**

### 効果

| | CPU（gallery、`NXE_GALLERY_HZ=30`） |
|---|---|
| 対策前 | 22.6 / 22.4 / 22.9 % |
| **対策後** | **約 9 %** |

アイドルの窓は 0.6 %。**ただし体感は A を直すまで変わらなかった。**

## 外した仮説

全部、実機で確認して外れたもの。**同じ思い込み（＝ CPU と描画の話だと思う）から
出ている**ので、まとめて残しておく。

| 仮説 | やったこと | 結果 |
|---|---|---|
| フレームのコストが高い | 上の 7 つ | CPU は 1/4。**症状は変わらない** |
| swap がホストのラン ループを止めている | シングルバッファ化 | 数字は最高。**ホストで窓が真っ黒**。撤回 |
| 毎フレームの `setNeedsDisplay:` | 削除 | **悪化**。撤回 |
| `NSOpenGLView` にレイヤーが無い | `setWantsLayer:` | 変化なし |
| **ホストの窓の `NSOpenGLView` が窓を壊す** | `IOSurface` + `CALayer` に作り替え | **症状は残った。**（この作り替え自体は動いたが、外れた仮説のための 400 行の unsafe FFI だったので、原因判明後に**落とした**） |
| 合成側が詰まっている | `WindowServer` を両状態で `sample` | **同一** |
| マルチディスプレイ／レート混在（120 + 144 Hz） | 1 台にして再現 | **変わらない** |

## 踏んだこと — 起動中のホストに install すると落ちる

実機確認の初回で **Studio One が Velour を刺した瞬間に落ちた。**

```
EXC_BAD_ACCESS / SIGKILL (Code Signature Invalid)
termination: CODESIGNING / Invalid Page
```

`cp -R` は既存のバンドルに**マージ**して Mach-O をその場で書き換えるので
**inode が変わらない**。ホストがそのファイルを既に map していると、次にページ
インしたときに署名と中身が合わず、macOS がホストごと殺す。

`mise run install` は**先に消してからコピーする**ようにした。**それでもホストは
落としてから入れるのが正しい。**

## 測り方

**アイドルの窓はコストゼロのはず**、が元からの規則
（`.agents/rules/vizia.md`）。**動いている窓**は測られていなかった。

```bash
# アイドル（従来のテスト）        → 0.6 %
mise run gallery

# 動いている窓                    → 約 9 %
NXE_GALLERY_HZ=30 mise run gallery

# スクロール（部分再描画が効かない唯一のケース。プラグインの窓は該当しない）
NXE_GALLERY_SCROLL=60 mise run gallery
```

CPU は起動分が混ざらないよう、開始後しばらくしてから `ps -o cputime=` の差分で
取る。

ホストで測るときは、**窓を前面に開き、実際に音を通した状態で**撮る。無音だと
1 % しか出ない:

```bash
sample <daw-pid> 5 -f ~/Desktop/open.txt
grep -c "vizia\|baseview\|femtovg" ~/Desktop/open.txt   # 0 なら撮れていない
```

**そして「重い」の正体が CPU とは限らない。** 忙しくないのに遅いなら、
`WindowServer` を撮る、機能を 1 つずつ消したビルドで挟み撃ちにする、という
順で疑う。

## 上流へ

どれも投げていない。**優先度は 1 番が飛び抜けて高い** — baseview を使う
プラグイン全部に効いているはずなので。

1. `setMouseCoalescingEnabled: NO` をやめる（baseview）
2. 見えない背景・枠・アウトラインを描かない（vizia）
3. 部分再描画（vizia）
4. 内容でサイズが決まらないビューはテキスト変更で再レイアウトしない（vizia）
5. フレーム タイマー 60 Hz と入力での即時描画（baseview / vizia）

フォーク: [`narusenia/vizia`](https://github.com/narusenia/vizia) `nxe-2026-08-31c` /
[`narusenia/baseview`](https://github.com/narusenia/baseview) `nxe-2026-08-31c`
