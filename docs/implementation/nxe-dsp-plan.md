# `nxe-dsp` 実装計画

プラグインが**通っている音について見せるもの**を作る。音は変えない。

`nxe-ui` と対になるクレート。あちらが「見せ方」を持ち、こちらが「見せる値」を
作る。どちらもホストを知らない。

- 状態と依存の一覧は [`backlog.md`](backlog.md)
- 順序は [`roadmap.md`](roadmap.md)
- クレートの位置づけは [`../specifications/architecture.md`](../specifications/architecture.md)

## なぜ 1 個目のプラグインで共通クレートを作るのか

architecture.md は「共通 DSP クレートは 2 個目のプラグインが必要としたときに
作る」と決めている。**解析はその例外**（2026-08-26）。レベル・ステレオ像・
スペクトラムは**どのプラグインでも同じもの**で、何が共通かを考える必要が無い。
再利用が決まっているものに YAGNI を当てても、置き場所が 1 個目のプラグインの
中になるだけで得が無い。

音を作る部品（遅延線・one-pole・スムージングノイズ）は今も `doubler-core` の中。

## DSP-1 — 音声スレッドから UI への受け渡し ✅

`Handoff<N>`。`AtomicU32` に `f32` のビットを置くだけ。

- **完了条件**: 音声スレッドが書き、UI が読める。確保もロックも無い ✅
- **決めたこと**: **latest-wins で、破れた読みを許す。** 読み手は 60 Hz の
  再描画で、2 回の書き込みが混ざったフレームを 1 枚見ることはあっても、
  減衰するメーターの上では誰にも見えない。整合性を買うにはロックか三重
  バッファが要り、音声スレッドはどちらも待てない（`REQ-DBL-011`）
- **決めたこと**: `AtomicU32` + `to_bits`。float の atomic クレートを足しても
  命令は同じで、依存だけ増える

## DSP-2 — ステレオ像の分布 ✅

`PanScope<BINS>`。方向ごとのエネルギー。

- **完了条件**: 中央の音が中央のビンに、片側の音が端のビンに入る。無音は
  何も動かさない。減衰がサンプルレートに依らない ✅
- **決めたこと**: **1 サンプルごとではなく短い窓（64 サンプル）ごと。**
  2 つの波形の瞬間比は、ほとんどの素材で端から端まで飛ぶ。数ミリ秒足して
  はじめて読める数字になる
- **決めたこと**: 振幅ではなく**エネルギー**で測る。静かな側が大きい側と
  同じだけ引っ張らない
- **決めたこと**: 出力は**絶対尺度**（両チャネル振り切りが `1`、無音が `0`）。
  「描く側が正規化する」で始めたが、**最大値で正規化すると音が止まっても絵が
  消えない** — 全ビンが同じ率で減衰するので比が変わらないから。絶対値なら
  音が消えたぶんだけ絵も消える

## DSP-3 — スペクトラム ✅

`Spectrum<BANDS>`。対数間隔の定 Q バンドごとのレベル。

- **完了条件**: 帯域の中心の正弦波がその帯域を立て、離れた帯域を立てない。
  無音で落ちる。ナイキストを超える帯域が暴れない ✅
- **決めたこと**: **FFT ではなくフィルタバンク。** 描く先の軸が対数だから。
  FFT のビンは線形で、20 Hz を分解するには 4096 点（表示が 85 ms 遅れる）が
  要るうえ、10 kHz より上では誰も要らない解像度に大半のビンを使う。
  バンクなら**オクターブあたりの分解能が一定**で、これは描く軸そのもの。
  窓もブロックバッファも要らず、依存も増えない
- **決めたこと**: 追従は**上が速く下が遅い**（10 ms / 250 ms）。片方だけだと
  トランジェントを取り逃すか、いつまでも滲む
- **決めたこと**: dB にしない。床をどこに置くかは描く側の判断
- **測定**（2026-08-26、M シリーズ、512 サンプル / 48 kHz）:
  `PanScope<24>` が **0.38 µs**、`Spectrum<32>` が **14.7 µs**。
  Doubler のエンジン 70 µs と合わせて 85 µs で、予算 533 µs の **16%**
  （1 コアの 0.8%）

## DSP-4 — レベル（IN / OUT メーターの値）✅

`Level`。1 チャネルの peak・ピークホールド・RMS を、バリスティクス付きで出す。

**Velour の IN / OUT メーターが要求する**（`REQ-VEL-013` / `REQ-VEL-018`）。
Doubler は使わなかったので今まで無かった。

- **完了条件**: フルスケールの正弦波で peak が 1 を指し、RMS が `1/√2` を
  指す。無音で落ちる。弾道がサンプルレートに依らない ✅
- **決めたこと**: 出力は**絶対振幅**（dB にしない）。`Spectrum` と同じ理由 —
  床をどこに置くかは描く側の判断
- **決めたこと**: **メーターの規格に寄せない。** VU / PPM / K-system のどれかを
  名乗ると、名乗った通りの弾道であることを要件にしないといけなくなる。ここが
  要るのは「IN と OUT が同じ音量か」の判断で、必要なのは**両者が同じ弾道である
  こと**だけ。同じ構造体を 2 回使えばそれは保証される
- **決めたこと**: **ピークホールドは DSP 側が持つ。** `Handoff` は latest-wins で
  読みを取りこぼすので、UI 側で最大値を追うと**捕まえるためにある山**を黙って
  見落とす
- **決めたこと**: アタックは即時。待っていたトランジェントを外すメーターは、
  少し長く保持しすぎるメーターより悪い
- **測定**: 未実施。Velour のエンジンと一緒に測る（`REQ-VEL-016`）
- **依存**: DSP-1

## `Spectrum` を 2 インスタンス使う（新規コードなし）

Velour は**原音**と**生成バス**の 2 本を重ねて描く（`REQ-VEL-018`）。
`Spectrum<BANDS>` は const generic なので 2 つ作るだけで、コードは足さない。

- バンド数を 32 → 48〜64 に上げたい。倍音（H2 は 1 オクターブ上、H3 は
  1.58 オクターブ上）が別の帯域に落ちる解像度が要る
- **コストは実測してから決める。** `Spectrum<32>` が 14.7 µs だったので
  64 × 2 で 60 µs 前後の見込み。予算 533 µs に対しては余裕があるが、
  Velour は 4x オーバーサンプルのエンジンと同居する（`REQ-VEL-016`）
