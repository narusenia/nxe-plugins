## 並べる基準

順序は好みではなく、次の 4 つで決めている。上にあるものが強い。

### 0. 前提が崩れると後続が無駄になるものを先に

Doubler の音は 2 タップクロスフェードのピッチシフタで決まる。**±50 cent の
範囲で継ぎ目が聞こえないという前提が崩れたら、方式ごと選び直す**ことになり、
その上に載せたボイスエンジン・Humanize・UI がすべて書き直しになる。

だから `DBL-2` は**ゲート**として扱った。完了条件に「耳で確認し、判断を計画に
追記する」が入っていたのはこのため。駄目なら `REQ-DBL-002` に戻って WSOLA を
再検討する段取りだった（そのための方式の比較は要件に残してある）。

**ゲートは通った。** 2026-08-25、Ableton Live で CLAP と VST3 の両方を確認し、
ラップのクリックも質感の劣化も無し。方式は回転タップで確定。

`DBL-4` を早く置いているのも同じ理由。UI を持たずホストの既定パラメータ UI で
音を出せる状態を先に作れば、ゲートの判断を最短で下せる。

### 1. パラメータ集合が固まるまで UI に投資しない

UI はパラメータの形に強く縛られる。`Detune` の範囲が変わる、形状層の意味が
変わる、`Source` のモードが増える — どれが起きても UI を作り直す。

だから UI はフェーズ 3。音を決めるフェーズ 2 が終わるまで `nxe-ui` にも
着手しない。**足場を先に作りたくなるが、作らない**（gallery が無いと UI は
書けないが、UI を書き始めるのがフェーズ 3 なら gallery が必要になるのも
フェーズ 3）。

例外は `INFRA-1` だけ。これが無いと `DBL-4` がバンドルできないので
フェーズ 0 に置く。

### 2. 配布は音と UI が固まってから

リリースの CI は、配布するものが決まってから作るのが一番安い。バンドルの
中身が変わるたびにワークフローを直すことになるのを避ける。プルリクエストの
CI（`INFRA-2`）も、コードがまだ空に近いうちは守るものが無い。

### 3. 使う人がまだ居ないものは最後

`UI-8`（Meter）と `UI-9`（ToggleSwitch）は Doubler が使わない。次のプラグインが
必ず要るという判断で作るが、**実戦で検証されないまま置くもの**なので、
検証されるものを全部済ませた後に回す。使うプラグインの計画が立った時点で
前倒しする。

## フェーズ

### フェーズ 0 — 骨格

`INFRA-1`

空のクレート 3 つと xtask が、バンドルまで通る状態にする。音は出ない。
この 1 単位だけを先にやるのは、`DBL-4` がバンドルを必要とするため。

### フェーズ 1 — 音が出るまでの最短経路

`DBL-1` → `DBL-2`（ゲート） → `DBL-3` → `DBL-4`

遅延線 → シフタ → ボイスエンジン → nih-plug ラッパ。UI は持たず、ホストの
既定パラメータ UI で音を確認する。**このフェーズの目的は「狙った音の方向に
居るか」を判断できる状態を作ること**で、機能の網羅ではない。Humanize も
Tone も Source モードもまだ無い。

### フェーズ 2 — 音を決める

`DBL-5`（Humanize） / `DBL-6`（Source） / `DBL-7`（Tone） → `DBL-8`

3 つは互いに依存しないので順序は自由。`DBL-8`（スムージングと非依存性）は
3 つが揃ってからまとめて詰める。ここが終わった時点でパラメータ集合が確定し、
UI に着手できるようになる。

### フェーズ 3 — UI

`UI-1` → `UI-2` / `UI-3` → `UI-4` / `UI-5` / `UI-6` / `UI-7` / `UI-10` →
`DBL-9` → `DBL-10` → `DBL-14` → `DBL-11` → `DBL-15`

全単位完了。積み残しの小物は `backlog.md` の「積み残し」表。

`nxe-ui` の足場（トークンと gallery）から始め、共通のふるまいを 1 箇所に置いて、
その上にウィジェットを載せる。プラグイン側は マクロ層 → Voice Field →
Detail 表 の順。**Voice Field が Detail 表より先**なのは、図が既定表示の主役で、
表はその補助だから。

`DBL-10` が `DBL-5` と `DBL-6` に依存しているのは、点の揺れと 2 つ目の基準点を
描くために Humanize と Source が動いている必要があるため。同じ理由で `DBL-14`
（Filter View）は `DBL-7` に依存する。

図（Voice Field、Filter View）が表より先なのは、どちらも既定表示の主役で、表は
その補助だから。

`DBL-15`（ミラー編集）は最後。図と表の**両方**に同じ規則で効かないといけない
ので、両方が動いてから入れるほうが、片方に合わせた実装を後で直すより安い。

### フェーズ 4 — 出荷

`INFRA-2` → `INFRA-3` / `DBL-12` → `DBL-13`

CI を整え、CPU 予算を測り、最後に実素材で既定値を詰める。`DBL-13` を最後に
置くのは、プリセットを持たない代わりに既定値で成立させる方針
（`REQ-DBL-013`）なので、**全機能が揃った状態でしか詰められない**ため。

### フェーズ 5 — 使う人がまだ居ないもの

`UI-9`

基準 3 のとおり。**`UI-8`（`Meter`）はここから外れた** — Velour の IN / OUT が
使う（`REQ-VEL-013`）ので、フェーズ 6 の共通クレート側に移る。

`UI-9`（`ToggleSwitch`）は 2 個目のプラグインでも要らなかった。3 個目でも
要らなければ計画から落とす。

### フェーズ 6 — Velour

順序:

1. **共通クレート先** — `DSP-4`（`Level`）→ `UI-8`（`Meter`）→
   `UI-13`（`BandField`）。**完了**
2. **仕様と計画** — 要件・DSP 仕様・UI 仕様・実装計画。**完了**
3. **Velour 本体** —
   `VEL-1` → `VEL-2` → `VEL-3` → `VEL-5` → `VEL-4` →
   `VEL-6` / `VEL-8` → `VEL-7` / `VEL-9` → `VEL-10` →
   `VEL-11` → `VEL-12` → `VEL-15` → `VEL-13` → `VEL-14` →
   `VEL-16` → `VEL-17`

**`VEL-5`（ラッパ）が `VEL-4`（TEXTURE）より前**なのは基準 1 の裏返し。
`TEXTURE` を Clear 固定にしておけば、帯域生成器が繋がった時点で音が出せる。
「原音に何かが足されている」を早く聴けるほど、その後の判断が速い。Doubler で
`DBL-4` を早く置いたのと同じ。

**`VEL-8`（Guard）は `VEL-3` にしか依存しない**ので、`VEL-4` 以降と並べられる。
`VEL-15`（解析の配線）が `VEL-13` より前なのは、メーターと 2 本の曲線に
渡す値が無いと UI 側を検証できないため。

**共通クレートを先にやるのは例外の判断。** 基準 1（パラメータ集合が固まるまで
UI に投資しない）に反しているように見えるが、`UI-13` / `UI-8` / `DSP-4` は
**Velour のパラメータの形に依存しない**。`BandField` は Hz も dB も知らず、
正規化した x と 0..=1 の高さしか受け取らない（`REQ-VEL-013`）。だから Velour の
値が動いても作り直しにならない。加えて gallery で単体検証できるので、
`velour` クレートが 1 行も無い状態で進められる。

**Velour のゲートは `VEL-1`、倍音の正規化**（`REQ-VEL-003` の「`k` を振っても
基音が ±0.1 dB 以内」）。Doubler でピッチシフタをゲートにしたのと同じ理由で、
ここが崩れると `REQ-VEL-009` の 4 層の直交が成立せず、**パラメータの意味づけ
ごとやり直し**になる。UI もマクロの意味も全部その上に載っている。

**違いは、このゲートが耳ではなく単体テストで通ること。** Doubler の `DBL-2` は
ホストで聴くまで判断できず、だから `DBL-4`（ラッパ）を前倒しする必要があった。
`VEL-1` は正弦波を入れて倍音の比を測れば済むので、`velour-core` の中で閉じる。

**次に危ないのは 4x で折り返しが −60 dB を切るか**（`REQ-VEL-005`）。切れない
場合に倍率で殴るのは最後で、まず `k` の上限を見直す（`REQ-VEL-020`）。

### Velour の後 — Sparkleur

Sparkleur（マルチバンドダイナミクス + Harmonic Sparkle）を **Velour より後に
置いた理由**:

- Sparkleur の中核は per-band の**ダイナミクス**（検波・ゲイン計算・帯域間の
  リンク・upward compression）で、Doubler のピッチシフタより一段重い新規 DSP。
  しかも効いているかの判断が耳頼み
- Velour の中核は帯域ごとの waveshaper で、**倍音次数を測れる = テストが書ける**
- **Velour が作る 3 つを Sparkleur がそのまま使う** — オーバーサンプラ、
  倍音生成カーブ、相対バランスの検出器（Sparkleur の De-Harsh は Velour の
  Harsh Guard と同じもの）。逆向きに再利用できるものはほぼ無い
- Sparkleur は「OTT + Exciter + Widener + Transient」の 4 製品ぶんで、
  **v1 の線引き自体が難問**。的の小さい方を先に通す

これらは `velour-core` に置き、**共通クレートには上げない**
（`architecture.md` の「2 個目が必要とするまで」）。ただし**パラメータ構造体を
知らない自立したモジュールとして書き**、移動がファイルの移動だけで済む状態に
する（`REQ-VEL-015`）。
