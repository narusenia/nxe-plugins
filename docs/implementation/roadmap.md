## 並べる基準

順序は好みではなく、次の 4 つで決めている。上にあるものが強い。

### 0. 前提が崩れると後続が無駄になるものを先に

Doubler の音は 2 タップクロスフェードのピッチシフタで決まる。**±50 cent の
範囲で継ぎ目が聞こえないという前提が崩れたら、方式ごと選び直す**ことになり、
その上に載せたボイスエンジン・Humanize・UI がすべて書き直しになる。

だから `DBL-2` は**ゲート**として扱った。完了条件に「耳で確認し、判断を計画に
追記する」が入っていたのはこのため。駄目なら `REQ-DBL-002` に戻って WSOLA を
再検討する段取りだった（そのための方式の比較は要件に残してある）。

**ゲートは通った。** 2026-08-25、Ableton Live で CLAP と VST3 の両方を確認し、
ラップのクリックも質感の劣化も無し。方式は回転タップで確定。

`DBL-4` を早く置いているのも同じ理由。UI を持たずホストの既定パラメータ UI で
音を出せる状態を先に作れば、ゲートの判断を最短で下せる。

### 1. パラメータ集合が固まるまで UI に投資しない

UI はパラメータの形に強く縛られる。`Detune` の範囲が変わる、形状層の意味が
変わる、`Source` のモードが増える — どれが起きても UI を作り直す。

だから UI はフェーズ 3。音を決めるフェーズ 2 が終わるまで `nxe-ui` にも
着手しない。**足場を先に作りたくなるが、作らない**（gallery が無いと UI は
書けないが、UI を書き始めるのがフェーズ 3 なら gallery が必要になるのも
フェーズ 3）。

例外は `INFRA-1` だけ。これが無いと `DBL-4` がバンドルできないので
フェーズ 0 に置く。

### 2. 配布は音と UI が固まってから

リリースの CI は、配布するものが決まってから作るのが一番安い。バンドルの
中身が変わるたびにワークフローを直すことになるのを避ける。プルリクエストの
CI（`INFRA-2`）も、コードがまだ空に近いうちは守るものが無い。

### 3. 使う人がまだ居ないものは最後

`UI-8`（Meter）と `UI-9`（ToggleSwitch）は Doubler が使わない。次のプラグインが
必ず要るという判断で作るが、**実戦で検証されないまま置くもの**なので、
検証されるものを全部済ませた後に回す。使うプラグインの計画が立った時点で
前倒しする。

## フェーズ

### フェーズ 0 — 骨格

`INFRA-1`

空のクレート 3 つと xtask が、バンドルまで通る状態にする。音は出ない。
この 1 単位だけを先にやるのは、`DBL-4` がバンドルを必要とするため。

### フェーズ 1 — 音が出るまでの最短経路

`DBL-1` → `DBL-2`（ゲート） → `DBL-3` → `DBL-4`

遅延線 → シフタ → ボイスエンジン → nih-plug ラッパ。UI は持たず、ホストの
既定パラメータ UI で音を確認する。**このフェーズの目的は「狙った音の方向に
居るか」を判断できる状態を作ること**で、機能の網羅ではない。Humanize も
Tone も Source モードもまだ無い。

### フェーズ 2 — 音を決める

`DBL-5`（Humanize） / `DBL-6`（Source） / `DBL-7`（Tone） → `DBL-8`

3 つは互いに依存しないので順序は自由。`DBL-8`（スムージングと非依存性）は
3 つが揃ってからまとめて詰める。ここが終わった時点でパラメータ集合が確定し、
UI に着手できるようになる。

### フェーズ 3 — UI

`UI-1` → `UI-2` / `UI-3` → `UI-4` / `UI-5` / `UI-6` / `UI-7` / `UI-10` →
`DBL-9` → `DBL-10` → `DBL-14` → `DBL-11` → `DBL-15`

全単位完了。積み残しの小物は `backlog.md` の「積み残し」表。

`nxe-ui` の足場（トークンと gallery）から始め、共通のふるまいを 1 箇所に置いて、
その上にウィジェットを載せる。プラグイン側は マクロ層 → Voice Field →
Detail 表 の順。**Voice Field が Detail 表より先**なのは、図が既定表示の主役で、
表はその補助だから。

`DBL-10` が `DBL-5` と `DBL-6` に依存しているのは、点の揺れと 2 つ目の基準点を
描くために Humanize と Source が動いている必要があるため。同じ理由で `DBL-14`
（Filter View）は `DBL-7` に依存する。

図（Voice Field、Filter View）が表より先なのは、どちらも既定表示の主役で、表は
その補助だから。

`DBL-15`（ミラー編集）は最後。図と表の**両方**に同じ規則で効かないといけない
ので、両方が動いてから入れるほうが、片方に合わせた実装を後で直すより安い。

### フェーズ 4 — 出荷

`INFRA-2` → `INFRA-3` / `DBL-12` → `DBL-13`

CI を整え、CPU 予算を測り、最後に実素材で既定値を詰める。`DBL-13` を最後に
置くのは、プリセットを持たない代わりに既定値で成立させる方針
（`REQ-DBL-013`）なので、**全機能が揃った状態でしか詰められない**ため。

### フェーズ 5 — 使う人がまだ居ないもの

`UI-9`

基準 3 のとおり。**`UI-8`（`Meter`）はここから外れた** — Velour の IN / OUT が
使う（`REQ-VEL-013`）ので、フェーズ 6 の共通クレート側に移る。

`UI-9`（`ToggleSwitch`）は 2 個目のプラグインでも要らなかった。3 個目でも
要らなければ計画から落とす。

### フェーズ 6 — Velour

順序:

1. **共通クレート先** — `DSP-4`（`Level`）→ `UI-8`（`Meter`）→
   `UI-13`（`BandField`）。**完了**
2. **仕様と計画** — 要件・DSP 仕様・UI 仕様・実装計画。**完了**
3. **Velour 本体** —
   `VEL-1` → `VEL-2` → `VEL-3` → `VEL-5` → `VEL-4` →
   `VEL-6` / `VEL-8` → `VEL-7` / `VEL-9` → `VEL-10` →
   `VEL-11` → `VEL-12` → `VEL-15` → `VEL-13` → `VEL-14` →
   `VEL-16` → `VEL-17`

**`VEL-5`（ラッパ）が `VEL-4`（TEXTURE）より前**なのは基準 1 の裏返し。
`TEXTURE` を Clear 固定にしておけば、帯域生成器が繋がった時点で音が出せる。
「原音に何かが足されている」を早く聴けるほど、その後の判断が速い。Doubler で
`DBL-4` を早く置いたのと同じ。

**`VEL-8`（Guard）は `VEL-3` にしか依存しない**ので、`VEL-4` 以降と並べられる。
`VEL-15`（解析の配線）が `VEL-13` より前なのは、メーターと 2 本の曲線に
渡す値が無いと UI 側を検証できないため。

**共通クレートを先にやるのは例外の判断。** 基準 1（パラメータ集合が固まるまで
UI に投資しない）に反しているように見えるが、`UI-13` / `UI-8` / `DSP-4` は
**Velour のパラメータの形に依存しない**。`BandField` は Hz も dB も知らず、
正規化した x と 0..=1 の高さしか受け取らない（`REQ-VEL-013`）。だから Velour の
値が動いても作り直しにならない。加えて gallery で単体検証できるので、
`velour` クレートが 1 行も無い状態で進められる。

**Velour のゲートは `VEL-1`、倍音の正規化**（`REQ-VEL-003` の「`k` を振っても
基音が ±0.1 dB 以内」）。Doubler でピッチシフタをゲートにしたのと同じ理由で、
ここが崩れると `REQ-VEL-009` の 4 層の直交が成立せず、**パラメータの意味づけ
ごとやり直し**になる。UI もマクロの意味も全部その上に載っている。

**違いは、このゲートが耳ではなく単体テストで通ること。** Doubler の `DBL-2` は
ホストで聴くまで判断できず、だから `DBL-4`（ラッパ）を前倒しする必要があった。
`VEL-1` は正弦波を入れて倍音の比を測れば済むので、`velour-core` の中で閉じる。

**次に危ないのは 4x で折り返しが −60 dB を切るか**（`REQ-VEL-005`）。切れない
場合に倍率で殴るのは最後で、まず `k` の上限を見直す（`REQ-VEL-020`）。

### Velour の後 — Sparkleur

Sparkleur（マルチバンドダイナミクス + Harmonic Sparkle）を **Velour より後に
置いた理由**:

- Sparkleur の中核は per-band の**ダイナミクス**（検波・ゲイン計算・帯域間の
  リンク・upward compression）で、Doubler のピッチシフタより一段重い新規 DSP。
  しかも効いているかの判断が耳頼み
- Velour の中核は帯域ごとの waveshaper で、**倍音次数を測れる = テストが書ける**
- **Velour が作る 3 つを Sparkleur がそのまま使う** — オーバーサンプラ、
  倍音生成カーブ、相対バランスの検出器（Sparkleur の De-Harsh は Velour の
  Harsh Guard と同じもの）。逆向きに再利用できるものはほぼ無い
- Sparkleur は「OTT + Exciter + Widener + Transient」の 4 製品ぶんで、
  **v1 の線引き自体が難問**。的の小さい方を先に通す

これらは `velour-core` に置き、**共通クレートには上げない**
（`architecture.md` の「2 個目が必要とするまで」）。ただし**パラメータ構造体を
知らない自立したモジュールとして書き**、移動がファイルの移動だけで済む状態に
する（`REQ-VEL-015`）。

**この賭けは当たった**（2026-08-26）。Sparkleur の設計が済んだ時点で要求された
のは `shaper` / `oversample` / `biquad` / `envelope` / `guard` の 5 つで、
どれも Velour を知らないように書いてあるので**ファイルの移動で済む**
（`guard` だけ、Velour 語彙のしきい値を引数に出す一般化が要る）。
`density` / `texture` / `bands` は要求されなかったので `velour-core` に残る。
移動は Sparkleur の最初の単位（`SPK-1`）で、行き先は新クレート
**`nxe-audio`**（`REQ-SPK-015`、理由は `architecture.md`）。

**やってみて 2 つ外れた**（`SPK-1`）。1 つは**測定ヘルパの `harmonics` も
一緒に動いた**こと — 移す 5 つのテストが全部それで書かれていて、依存の向きが
逆だから残せない。もう 1 つは `envelope` で、時定数と `REFERENCE_DB` は
**歌に対して耳で決めた数**なので機構だけ移して数は `velour-core` に残した。
「ファイルの移動で済む」は `shaper` / `oversample` / `biquad` の 3 つには
そのまま当たった。

### Sparkleur の中での順序

**v1 の線引きは設計で解いた**（`REQ-SPK-019` / `REQ-SPK-020`）。WIDTH と PUNCH を
v2 に置き、核をマルチバンドダイナミクス + 動的な倍音生成に絞った。理由:

- **WIDTH はモノ互換の約束を壊す唯一の機能**で、テストの道具立てが全部新規
- **PUNCH は「効いたか」が一番耳頼み**。しかも Sparkle の検出器が既に
  トランジェントを見ているので、**それを 1 個作って納得してから**足すほうが安全

実装単位の順序は `plugins/sparkleur/docs/implementation/sparkleur-plan.md`。
**ゲートは `SPK-2`（分割の和が ±0.1 dB 以内で平坦）** — ここが通らないと
「全部 0 で何もしない」が成立せず、その上の全部が意味を持たない。
Velour の `VEL-1` と同じ位置。

## Sparkleur の後 — 構想 6 本の順序

構想は [`../../concepts/`](../../concepts/) に 6 本ある。**この節は順序の根拠
だけを持ち、各本の中身には立ち入らない**（要件を書く時点で、その本の
`plugins/<name>/docs/` に移る）。

```text
Air → Diorama → Pumice → Vocal Glue → Impact → Growl
                          ↑
                 Bass Density はどこにでも差し込める
```

**Pumice は構想 6 本の外から入った**（2026-09-01）。構想文書を持たず、
要件から直接書いた 1 本目。

### 並べた根拠

上の「並べる基準」に 1 つ足りない軸がある。**このリポジトリが一度もやって
いないホスト連携が要るか**だ。基準 0（前提が崩れると後続が無駄になる）の
変種で、しかも質が悪い: サイドチェイン入力・レイテンシ申告・MIDI・テンポ同期は
**どれも `cargo test` の中で確かめられない**。DAW を開くまで壊れているか
分からないものは、判断の速度を落とす。だから後ろに置く。

| | 新規ホスト連携 | 既存で足りる割合 | 他に貸せる新ブロック |
|---|---|---|---|
| Air | なし | 高 | ノイズ生成、M/S・脱相関、明るさ追従 |
| Bass Density | なし | **最高** | N 帯域クロスオーバー、Transient Restore、出力クリッパ |
| Diorama | なし | 中 | **初期反射** |
| Vocal Glue | サイドチェイン入力 | 中 | — |
| Impact | ルックアヘッド + レイテンシ申告 | 中 | ルックアヘッド |
| Growl | MIDI 入力、テンポ同期、ステップシーケンサ | 中 | フォルマントバンク |

**Air と Diorama が、残り全部の材料をほぼ作ってしまう。** 共有クレートの
規則（`architecture.md` の「2 個目が必要とするまで」、実務上は 3 個目）に
そのまま乗る:

- **ノイズ生成器** — Air / Growl の `TEETH` / Vocal Glue の `AIR Cohesion` の 3 つ
- **M/S と脱相関** — Air / Diorama / Vocal Glue / Impact の 4 つ
- **初期反射** — Diorama / Vocal Glue / Impact の 3 つ

Air で前の 2 つ、Diorama で 3 つ目が出揃う。Velour が Sparkleur に
オーバーサンプラと倍音カーブと検出器を渡したのと同じ形。

### Vocal Glue を 3 番目に置く理由

いきなり作ると**初期反射・サイドチェイン・スペクトル整合の 3 つが同時に新規**に
なる。Diorama を挟むと、初期反射を「声 1 本・サイドチェイン無し」という
簡単な問題で先に片付けられて、Vocal Glue に残るのは `Spectral Cohesion` と
`LEAD ANCHOR` だけになる。Sparkleur を Velour の後ろに置いたのと同じ判断。

### Bass Density がどこにでも入る理由

**Sparkleur の再利用率が一番高い** — 帯域分割・上下コンプ・サチュレーション・
トランジェント検出が全部ある。新規は「Sub は壊さない」規則と出力クリッパと
サブ再構成くらい。新しく学ぶことがほとんど無い代わりに、**一番早く 1 本
増える**。前後関係が無いので、息継ぎが要るところに差し込む。

### 要件を書く前に潰しておくことだった 3 つ

**全部片付いた**（2026-08-27）。どう決着したかは各要件書が正で、ここには
結論だけ残す。

- **Air と Sparkleur の境界** → 生成器ではなく**層の扱い**で引いた。
  Follow Engine と Stereo Air が Air の正体で、追従の深さが 0 なら Velour、
  トランジェントだけなら Sparkleur という**座標として境界が監査できる**
  （`REQ-AIR-002`）
- **Vocal Glue の `Timing Cohesion`** → **落とした**。バスでは情報が無い。
  狙いは `ATTACK CENTERING` が別の手段で達成する（`REQ-GLU-019`）。
  **同じ形の問題が `Spectral Cohesion` にもあった** — 「Lead だけ明るい」は
  和から判別できないので、「和の傾きを目標へ寄せる」に書き直した
  （`REQ-GLU-003`）
- **`LEAD ANCHOR` のサイドチェイン** → **v2 に落とした**（`REQ-GLU-020`）。
  Glue には既に `Spectral Cohesion` という新規があり、未検証のホスト連携を
  重ねると失敗の原因が切り分けられない

### 各本のゲート

Velour の `VEL-1`、Sparkleur の `SPK-2` と同じ「崩れたら方式ごと選び直す」
前提。要件を書いた 3 本は決まっている。

| | ゲート | 耳が要るか |
|---|---|---|
| Air | `WIDTH` 全域でモノ和に櫛形が出ない（`REQ-AIR-008`） | 不要 |
| Diorama | `DEPTH` 全域でラウドネスが ±0.5 dB（`REQ-DIO-008`） | 不要 |
| Vocal Glue | 和の傾きが目標へ単調に寄る（`REQ-GLU-003`） | 不要 |

3 本とも**単体テストで通る**。Doubler の `DBL-2` のようにラッパを前倒しして
実機で聴く必要が無いので、コアを先に固められる。


## Pumice を Vocal Glue の前に置く理由

Pumice（単体ボーカルの動的共鳴抑制）は
[`REQ-PUM.md`](../../plugins/pumice/docs/requirements/REQ-PUM.md)。

**「Vocal Glue が安くなるから」ではない。** その理屈は最初に考えたもので、
**方式を FFT に決めた時点で崩れた**。Vocal Glue の `Spectral Cohesion`
（`REQ-GLU-003`）は `RelativeGuard<N>` の一般化＝減算型バンドパスバンクで
作ると決まっていて、**Pumice の STFT エンジンはそこに何も渡さない**。
Vocal Glue は自分で減算型を書く。

**置く理由は「単体で価値がある」こと。** 挿す対象が違う — Vocal Glue は
複数の声が混ざったバス、Pumice は 1 本のボーカル。ラインの他の 5 本は
全部「足す・動かす」製品で、**引く製品が 1 本も無い**。

**先にやる理由は、リスクが 2 つとも早く分かること。**

1. **PDC**（`PUM-1`）。ラインで初めてレイテンシを申告する。**空に近い
   ラッパのうちに 4 ホストで確かめる** — 基準 0 そのもので、駄目なら
   方式ごと選び直す。この確認は Pumice のためだけでなく、**将来
   ルックアヘッドや直線位相を持つ製品すべての前提**になる
2. **音声パスの FFT**（`PUM-8`）。`nxe_dsp::spectrum` も Sparkleur の
   spectral flux も「もっと安いもので同じ仕事ができる」で FFT を却下して
   いる。**Pumice で実測が出れば、その判断が今も正しいかが分かる**

**Vocal Glue はこの 2 つのどちらも要らない**（レイテンシ 0、FFT 無し）ので、
Pumice の結果を待つ必要が無い。**待つ必要が無い側を後ろに置いた。**

### Pumice の中での順序

```text
PUM-1  PDC（ゲート）      ← 人が 4 ホストを開く。ここが全部の前提
PUM-2  OLA
PUM-3  STATIC（音が出る）  ← ホストの既定パラメータ UI で判断
PUM-4  ADAPTIVE（ゲート）  ← STATIC との比較でしか測れない
PUM-5〜9
UI-22  NodeField          ← パラメータ集合が凍ってから（基準 1）
PUM-10 窓
PUM-11 耳
```

**ゲートが 2 つあるのはラインで初めて。** 1 つ目は方式の前提（PDC）、
2 つ目は製品の主張（倍音を削らない）。**性質が違うので分けている** —
`PUM-1` が駄目なら FFT ごと捨てるが、`PUM-4` が駄目なら `ADAPTIVE` だけを
落として `STATIC` の製品として出せる。

**`UI-22`（`NodeField`）がリポジトリで一番大きい UI 投資。** `CurveView` は
x 固定、`BandField` は領域の端しか動かない。**自由な x 配置・追加・削除を
持つものが無い**ので 3 個目を作ることになり、`band.rs` が
「なぜ `CurveView` を拡張しなかったか」に書いた理屈がそのまま効く。
だから**一番後ろ**に置く（基準 1）。

## v0.2.0 — 5 本を作り直す

出荷済み 4 本と、未出荷の Diorama（旧 Diorama）を**まとめて `0.2.0` に
揃えて出す**。中身は 3 つ。

- **窓を fors 方向に作り直す**（5 本、`nxe-ui-plan.md` の `UI-15`〜`UI-20`）
- **Hard モード**（Sparkleur と Velour だけ、`SPK-21` / `VEL-19`）
- **`PUNCH`** を v2 から回収する（Sparkleur、`SPK-22`）

### Diorama を v0.2.0 に合流させた理由

**旧 UI の Diorama を世に出さないため。** UI の作り直しは共有クレート
`nxe-ui` を壊すので、先に Diorama を `0.1.0` で出すと「main に UI が入った
瞬間に Diorama も新テーマを拾う」形になり、**旧 UI で出荷された 1 本が
残る**。5 本を並べて 1 つの製品群に見せるのがこの版の狙いなので、それは
自分で壊しに行くことになる。

代償として、**`DIO-14` の聴き直し・`DIO-13` の既定値・実機での見た目**が
v0.2.0 のゲートに上がった。どれも人の耳と目が要る。

**見た目は 2026-08-31 に通った**（5 本とも、Hard と PUNCH も同じ日に）。
残っているのは **`DIO-14` の聴き直しと `DIO-13` の既定値**だけで、どちらも
Diorama——**この版で唯一の初出荷**——のもの。

### 並べた順序

```text
SPK-20 / VEL-18  天井の所在を測る     ← 基準 0（前提が崩れると後続が無駄）
DIO-15           Diorama への改名
SPK-21 / VEL-19  MODE（Soft / Hard）  ┐
SPK-22           PUNCH                ┘ ← 基準 1（パラメータ集合を先に固める）
UI-15 〜 UI-20   共通 UI の作り直し
SPK-23           Sparkleur の窓（型を決める）
VEL-20 / AIR-14 / DBL-17 / DIO-16     残り 4 本の窓
既定値・実機・タグ
```

**測る単位が先頭。** 「かかりが弱い」は耳の不満で、そこから実装に届く道は
測定しかない。`DIO-14` がまさにこの形だった — 「遠い近いに聞こえない」を測って
みたら、要件に書いてある処理が**実装されていなかった**。Hard は写像を持ち上げる
ものなので、止めているのが写像でなければ効かない。何が天井かを先に特定する。

**改名は早いほど安い。** ディレクトリと crate と ID を全部動かす機械的な変更
なので、窓の作り直しと重なると衝突が増えるだけで得が無い。

**`MODE` と `PUNCH` は UI より前。** 基準 1（パラメータ集合が固まるまで UI に
投資しない）がそのまま効く。どちらもパラメータが増える側で、UI を先に組むと
窓を 2 回組むことになる。

**Sparkleur の窓が先行**（`SPK-23`）。35 個で一番重く、グリッド・記号・寸法・
反転面の置き方をここで確定させてから残り 4 本に展開する。逆順にすると、軽い窓で
決めた型が重い窓で破綻して全部やり直しになる。`SPK-19` が 1 度そうなっている。

### Hard を 2 本に限った理由

**弱いと判断したのが Sparkleur と Velour の 2 本だから。** 4 本すべてに
`MODE` を置けばラインの語彙は揃うが、Doubler と Air では**中身の薄いスイッチ**
になる。「見えない保護は無いのと同じ」（`.agents/rules/ui.md`）の裏返しで、
**何も変わらないスイッチは信用を減らす**。

### v2 から `PUNCH` だけを回収した理由

**落とした理由が 1 つ消えたのは `PUNCH` だけ。** `REQ-SPK-020` が挙げた 3 つの
うち「検出器を先に 1 個作って納得してから」は `SPK-6` で解消していて、
「効いたかが一番耳頼み」も **crest factor（ピーク − RMS）**という測れる量で
受入条件が書ける。

残りは落としたままにする。

- **`REQ-SPK-019` WIDTH** — モノ互換の約束を壊す唯一の機能で、テストの道具立て
  （相関・M/S・モノ和）が全部新規。`REQ-SPK-011` を書き直すところから始まる
- **`REQ-VEL-019` DISTANCE** — マクロのマクロで、`REQ-VEL-010` の二層が三層に
  なる。出荷済みの既定値ができたので軌道は実測で決められるようになったが、
  この版には他に 2 つ入っている
- **`REQ-AIR-019`〜`021`** — Air は弱いと判断した本に入っていない。3 つとも
  約束（受入条件・位相・折り返し）を書き直すところから始まる

### この版でやらないと決めたこと

- **既定値の詰め直し。** Hard は完全なオプトインにする。既定値の変更は既存
  セッションを壊さないので安全側の変更だが、耳のサインオフが 2 本ぶん増える。
  Hard が入ったあとで「まだ弱い」が残るなら、そのとき動かす
- **guard の既定を下げる。** 保護は `REQ-SPK-008` / `REQ-VEL-006` が製品の
  約束として書いているもの。「先に guard が掛かる」が天井だった場合でも、
  既定ではなく写像側で解く
- **折り返しゲートを緩める。** Hard でも「4x で −60 dB 以下」を Soft と同じ
  測り方で通す。足りなければ `REQ-VEL-020` が定めた順序の最後の一段
  （OS 8x の新設）に進む
