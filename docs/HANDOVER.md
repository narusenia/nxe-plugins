## ホストの UI が重くなっていた — 本命は vizia のバグ 2 つ

**測って分かった。** `mise run gallery`（ホストも音もハートビートも無い、
ただ開いているだけの窓）が**アイドルで CPU 27.7 %**。`sample` で内訳を取ると
描画時間の **27 % が `fontdb::Database::query`**。

**バグ 1 — baseview が毎フレーム無条件に全画面を再描画していた。**
`Application::on_frame_update` が `should_redraw` を計算しているのに
`ViziaWindow::on_frame` が読んでいない。**`vizia_winit` は同じフラグを読んで
`request_redraw()` を呼んでいる**ので、baseview 側の書き忘れ。
macOS ではこのフレームタイマーが `CFRunLoopTimer` として**ホストのメイン
スレッドの run loop に載る**ため、僕たちの再描画がそのままホストの UI を
止めていた。

**バグ 2 — テキスト 1 個・1 フレームごとにフォントデータベースを全走査。**
`TextContext::sync_styles` が `fontdb::Database::query` をキャッシュせずに
呼ぶ。データベースには `load_system_fonts()` でシステムフォント全部が入って
いる。

**直した**: `narusenia/vizia` の `nxe-2026-08-27`（`patched-2024-05-06` +
2 コミット）に `[patch]` で差し替え。**`[patch]` はグラフ全体を書き換えるので
`nih_plug_vizia` の vizia も同じものになる** — 「完全に同一でなければならない」
は守られたまま。**アイドル 27.7 % → 0.9 %。**

**アイドルの窓は CPU を食わないはず**なので、食っていたらそれがバグ。
`ps -o %cpu` を `mise run gallery` に当てるだけで分かる。**上流に投げる価値が
ある。まだ投げていない。**

### 192 kHz / バッファ 64 で測った取り分（`sample` を Studio One に直接当てた）

**ホスト全体が 163.9 %** のとき、5 秒のサンプルでの内訳:

| | サンプル数 |
|---|---|
| **NXE Velour 全部**（音声 199 + UI 61） | **260** |
| UAD LA-2A | 3 804 |
| **iLok / PACE** | **8 601** |

1 スレッド = 2867 サンプル = 5 秒。**Velour は 1 コアの約 9 %**（音声 7 / UI 2）で、
PACE はその 33 倍。**重さの主因は僕たちではない。**

音声側の単体実測（`Engine::process` を直接回した）:

| | 48 kHz / 512 | 192 kHz / 64 |
|---|---|---|
| Air | 0.5 % | **1.8 %** |
| Velour 4x | 0.8 % | **3.3 %** |
| Velour 2x | 0.4 % | **1.8 %** |

**設計どおりの数字。** 1 サンプルあたりのコストは固定なので、192 kHz では
48 kHz の 4 倍になる。予算（`REQ-*-016`）は 48 kHz / 512 で書いてあるので、
**この設定は予算の外**。

**減らす余地は 1 つある**: 192 kHz で 4x を回すと内部 768 kHz になる。
オーバーサンプリングは「倍音が折り返す前にナイキストを上げる」ためのもので、
ホストが既に 192 kHz ならその仕事はホストがやっている。**倍率をホストレートから
決める**（内部レートを 192 kHz に揃える）と半分になる。

**ただし上蓋がホストレートに比例している**ので、そのまま倍率だけ下げると
折り返しの約束が変わる（Velour の `AIR_INPUT_CEILING` は `0.25 × ホストレート`
で、192 kHz では 48 kHz まで開く）。**上蓋と倍率を一緒に設計し直して、
各レートで折り返しを測り直す**単位が要る。**やるなら要件から。**

**今すぐ効く手はある**: `OVERSAMPLE` は画面に出ているので、192 kHz では
**2x にするだけで音声のコストが半分**になる。

## ハートビートも漏れていた（別件、こちらも直した）

**症状**: プラグインをインサートに挿すと Studio One の UI が重くなる。
4 本とも、どれでも起きる。**`v0.1.3` / `air-v0.1.2` で直っている** —
それより前は全部影響を受ける。**ただしこれは本命ではなかった**（本命は上の
vizia のほう）。

**原因**: 表示のハートビートを止める条件が**baseview では絶対に成立しない**。

```rust
while proxy.emit(UiEvent::Poll).is_ok() {   // ← 永久に true
    std::thread::sleep(ANALYSIS_INTERVAL);
}
```

`vizia_baseview::proxy::BaseviewProxy::send` は `lazy_static` のキューに
push して**無条件に `Ok(())` を返す**。ユニット構造体で窓への参照を持って
いないので、窓がまだあるかを知りようがない。

**帰結が 3 つ重なる**:

1. **ホストが窓を開くたびにスレッドが 1 本増え、閉じても止まらない。**
   ホストのプロセスが生きている限り溜まり続ける
2. そのキューは**プロセス全体で 1 本・ミューテックス付き・上限なし**で、
   **プロセス内のすべての vizia 窓が共有する**。漏れたスレッドが全部
   30 Hz で push する
3. キューを吸うのは `Application::on_frame_update` **だけ**なので、
   **エディタを全部閉じている間は誰も吸わない**。無制限に伸びて、
   次に開いた窓が 1 フレームでその全部を払う

**直した形**: 終了条件を**呼び出し側が持つもの**にした。
`nxe_ui::heartbeat::start` が `Lifeline` を返し、**それをモデルに入れる** —
窓のコンテキストが落ちるときに一緒に落ちるので、スレッドは 1 インターバル
以内に終わる。4 本とも同じ 1 箇所を呼ぶようになった（同じループが 4 つ
あったのを上げた）。

**`.agents/rules/vizia.md` に理由付きで書いた。** この vizia の
「コンパイルも通り、エラーも出さず、何もしない」の一覧に、
**「エラーも出さず、止まらない」**が 1 つ増えた形。

## ゲートの許容を ±1.0 dB に改訂した — ±0.5 dB は素材を跨いでは満たせない（`VDP-3 の実測`）

**帯域 EQ が信号の総パワーをどれだけ動かすかは、その信号が帯域にどれだけ
入っているかで決まる。** それは素材の性質で、パラメータからは分からない。

| 素材 | Presence 帯（2〜5 kHz）の割合 |
|---|---|
| ピンクノイズ | **10.3 %** |
| ホワイトノイズ | 13.4 % |
| 疎な倍音列のフレーズ | **1.2 %** |

`DEPTH` 全域での出力 RMS のばらつき（ゲートの要求は **0.5 dB**）:

| Presence の補正率 | ピンク | ホワイト | フレーズ | 最悪 |
|---|---|---|---|---|
| 0.00 | 1.46 | 1.79 | 0.22 | 1.79 |
| 0.50 | 0.63 | 0.96 | 0.62 | **0.96** |
| 0.75 | 0.26 | 0.57 | 1.00 | 1.00 |
| **1.00**（今） | **0.14** | **0.19** | **1.39** | 1.39 |

**最良の最悪値は補正率 0.6 付近で 0.8 dB**、ホワイトを外しても 0.5 で
**0.62 dB**。**どこにも 0.5 dB は無い。**

**原因の候補を 3 つ測って全部否定した。** テイルではない（500 ms 以降は厳密に
0）、測り方でもない（EBU 風の相対ゲートでも 1.38 dB、上位 4 分の 1 でも
1.21 dB）、タップのコヒーレンスでもない（ビブラート 1.5 % と息で 1.26 dB）。

**手は 3 つ。どれも判断が要る。**

1. **`depth::PRESENCE_COMPENSATION` を 0.5〜0.6 に下げる。** 全素材が
   0.6〜1.0 dB に収まる。**どれも 0.5 dB は満たさない**
2. **Presence の可動域（`+4 / −8 dB`）を狭める。** 表全体が比例して縮むので
   0.5 dB に入るが、**製品の主効果が小さくなる**
3. **`REQ-VDP-008` の受入条件を緩める**（±1.0 dB など）。残差は「音量が動く」
   より「音色が動く」に近い

**反射側は素材によらず正確に補正できている**（広帯域なので）。**壊れているのは
帯域 EQ の項だけ。**

## Vocal Depth で分かったこと（`VDP-1`〜`VDP-14`）

### `VDP-5`〜`VDP-12` の実測

| 何 | 実測 |
|---|---|
| `DAMPING` の 2 側のコーナー差 | **1.9 オクターブ**（6 kHz 上で 9 dB） |
| Transient が保つ高域 | 8 kHz 上で **+4.6 dB** |
| **直接音のモノ和の櫛形** | **0.0 dB**（対照のオールパスは 6 dB 以上） |
| `CLARITY` が普通の素材で戻す量 | **厳密に 0**（ピンク / ホワイト / 歌） |
| ブロックサイズ 1 / 64 / 512 / 4096 | **ビット一致** |
| 4 レート | 1 dB 以内 |
| **全マクロを 1 サンプルで端から端まで動かした段** | **背景の 1.0 倍**（対照 90 倍） |
| NaN 1 個のあと | クリーンな走行と **0.1 dB 以内**に戻る |
| 音声経路の確保 | **0 回**（カウンタが数えられることも確認） |
| **CPU（512 / 48 kHz、全部働いて）** | **20.9 µs / 予算 533** |

**踏んだ罠が 5 つ増えた。**

- **`DAMPING` が段を出していた（背景の 66 倍）。原因が 3 つ重なっていた。**
  ブロックレートでコーナーが跳んでいた / **バイパスの出入りでフィルタが空の
  状態から動き出していた** / **2 次セクションの係数差し替えがナイキスト近傍の
  極を励振していた**。3 つ目が本命で、**細かく retune するほど悪化する**
  （7 → 12 倍）という形で出た。**1 次 2 段に替えたら段は消え、CPU も安くなった**
- **`octave` を足す向きを間違えた。** コーナーを「下げる量」で持っているのに
  Transient のぶんを足していたので、1 オクターブ開きすぎて「保たれた量 0.0 dB」
  と出た。**符号は測るまで分からない**
- **無相関な 2 チャネルでは櫛形が作れない。** 対照実験にピンクとホワイトを
  入れていたが、無相関ならパワーで足し算になるのでどうチューニングしても
  櫛が出ず（2.5 dB）「櫛形なし」と読めた。**入力をセンターにする**
- **`pink` と `noise` は相関している。** `pink` は同じ白色列をフィルタした
  ものなので、L/R に入れても「無相関な 2 チャネル」にならない。M/S のパワー
  係数が予測 0.5 に対し実測 0.739 になって初めて分かった。**片方を逆順にする**
- **`±` と peak-to-peak を混同した。** ゲートの数を全部 peak-to-peak で測って
  おきながら「±0.5 dB」と比べていたので、**失敗の幅を 2 倍に見せていた**。
  実測の最悪は ±0.50 dB で、報告した「0.9 dB 足りない」は実際には 0.2 dB
  だった。**メトリックの単位はテストの中に書く**

### `VDP-1`〜`VDP-4`

**2 単位通った。** `VDP-1` はタップ 10 本 × 2 チャネル + 拡散 3 段 + 200 Hz HP、
`VDP-2` は Presence の並列帯（2〜5 kHz）+ Transient の検出（2〜8 kHz）。
テスト 20 本。

### `VDP-1` — 初期反射

| 何 | 実測 |
|---|---|
| 120 ms 以降のエネルギー | **−25.5 dB** |
| 250 ms / 500 ms 以降 | −140.7 dB / **厳密に 0** |
| `DEPTH` を 1 サンプルで 25 % 動かしたときの段 | **0.36**（対照 88） |
| 無音から厳密な 0 まで | **0.150 s**（予算 3 秒） |
| 4 レートの応答の差 | **0.08 dB 以内** |
| L/R の相関（同じ信号を両方に） | **−0.006** |

**設計時の値が 3 つ動いた。どれも実測が設計を否定した結果。**

- **タップ 13 → 10 本、最後のタップ 113 → 89 ms。** **拡散の尾は最後のタップに
  も乗る**ので、113 ms まで置くとエネルギーの 3 分の 1 が 120 ms の外に出た
  （−4.6 dB）。`dsp.md` に書いていた「120 ms までに 9 周して −47 dB」は
  **インパルスに対する**尾の計算で、タップ 1 本ごとの尾を数えていなかった
- **オールパス `g` 0.55 → 0.45、最長 11.9 → 7.9 ms。** 尾の長さを決めるのは
  **最長の段 × 周回数**
- **重みとバスのゲインを 5 ms でスムーズする機構が増えた。**
  「重みを動かすだけだからクリックは出ない」は間違い — **重みを動かすことは
  ゲインを動かすこと**で、段が背景の 11 倍出た

**罠が 2 つ増えた。**

- **対照実験が本番とほぼ同じ数字を出した。** ゲインを 4 分の 1 に跳ばす対照が
  104.89、直したはずの本番が 104.94。**`0.22` へ跳ぶのも `1.78` へ跳ぶのも
  1 からの 0.78 の段**だったから。**どちらが外れ値か分からない対照実験は
  対照実験ではない。** 今は「同じ動きをスムージング無しで」やる形にしてある
- **1 次の追従は目標に着かないことがある。** 歩幅 `remaining · coefficient` が
  値の ulp を下回ると加算が何も変えなくなり、収束は
  `ulp(w) / coefficient` ≒ **7e-6** で止まる。しきい値を `1e-6` に置いていたので
  **永遠に「まだ動いている」**状態になり、無音でも毎サンプル回していた

**`DelayLine` が `nxe-audio` に上がった。** `doubler-core` から移動
（**2 個目の客が要求した**ので規則どおり）。整数読み `read_whole` を足した —
タップ時刻が動かないので補間が要らず、**Catmull-Rom の 4 分の 1** で済む。

### `VDP-3` — 正規化

| 何 | 実測 |
|---|---|
| `DEPTH` 全域の RMS（ピンク / ホワイト） | **0.14 / 0.19 dB** |
| 同（疎な倍音列のフレーズ） | **1.39 dB** ← ゲート未通過 |
| 正規化を 1 に固定したときの同じ掃引 | 1.29 dB（**測定は失敗できる**） |
| 4 素材での正規化係数 | **完全一致**（信号に依存しない） |
| 名目 6 dB の cut で減るパワー（並列帯 / ピーキング） | **−0.18 / −0.71 dB** |
| 並列帯の裾の持ち上がり | **8.6 kHz で +0.57 dB** |

**設計時の値が 2 つ動いた。**

- **Presence は並列帯ではなくピーキング。** `x + (G−1)·BP(x)` は **`G` < 1 で
  帯域を下げない** — 帯域通過の位相のぶん裾が持ち上がり、**cut の 4 分の 3 が
  戻っていた**。`nxe_audio::biquad::Coefficients::peaking` を足した。
  **`REQ-VDP-004` が元々「シェルフ」と書いていたのは正しく、`dsp.md` を書く
  ときに並列帯へ直したのが間違いだった**
- **プローブの重みは対数格子の上では一様。** ピンクは 1 オクターブあたりの
  エネルギーが一定で、対数の 1 ステップはオクターブの一定割合なので、
  **`1/f` は格子の間隔が既に持っている**。掛けると二重に傾き、
  **20 Hz が 3 kHz の 150 倍**になる

**罠が 2 つ増えた。**

- **最悪値が帯域の外に出る。** 並列帯の裾の持ち上がりは **8.6 kHz** が最悪で、
  2〜5 kHz を見ていても気づかない
- **段の対照実験が「段なし」になった。** ピーキングは**係数を差し替えても
  状態が残る**ので、出力は段ではなくリング時間で歩く。スムージングを外しても
  段が出ず（0.99）、**対照実験を「素直なゲインとして跳ばす」形に作り直した**

### `VDP-4` — ラッパ

**音が出る。** CLAP と VST3、パラメータ **5 個**（`DEPTH` / `DIRECT` / `ROOM` /
`MIX` / `OUTPUT`）。`DAMPING` / `WIDTH` / `CLARITY` は宣言していない —
**何もしないコントロールを先に出さない**。id は鍵なので後から足すのは安全。

- **レイテンシは 0 で申告もしない。** 遅延線はあるが**反射は原音より遅れて
  来るもの**で、直接音の経路にバルク遅延が無い（`REQ-VDP-012`）
- **`MIX` = 0 のビット一致がエンジン単体のテストでは隠れていた。**
  エンジンが `mix` を内部で 5 ms スムーズしていて、**セッションを `MIX` = 0 で
  開いた最初の 5 ms が wet になる**。エンジンのテストは `set` のあとに
  `reset()` を呼んでいたので気づかなかった。**`mix` と `output` は呼び出し側が
  スムーズ済みの値を渡す**形に直した（正規化だけは内部でスムーズする）。
  **ラッパを書いて初めて出るバグ**で、`VEL-5` / `AIR-4` を早い順番に置いている
  理由がまた 1 つ増えた
- **`ParamPtr::update_smoother` は private。** `primed()` は Air と同じく
  フィールドごとに `smoothed.reset(value())` で書く

### `VDP-2` — 直接音

| 何 | 実測 |
|---|---|
| `DIRECT` 端から端の Presence 帯 | **14.79 dB**（うち Transient が 2.79 dB） |
| バースト列での開き具合 | **1.000** |
| ピンクノイズでの開き具合 | 0.150 |
| **定常信号への寄与**（Transient を切った同じ走行と比較） | **純音 0.045 dB / ピンク 0.000 dB**（予算 0.3 dB） |
| 入力ゲイン ±12 dB | 0.2 dB 以内 |
| パラメータ段の継ぎ目 | **0.40**（対照 3.17） |

**設計時の値が 2 つ動いた。**

- **Transient の検出を 2〜8 kHz の帯域通過の後ろに置いた。** 子音の居場所で
  あり、**`SNAP_RANGE_DB` を Air から借りる条件**でもある（`AIR-5` が同じことを
  要求している）
- **「定常状態で係数が厳密に 1」は間違いだった。** **正弦のパワーは周波数の
  2 倍でリプルする**ので、2 ms のフォロワはその一部を追い、80 ms は平均する。
  純音 110 Hz で開き具合 **0.204**。Air も定常正弦に 0.023 を出している

**`DIRECT` と `DEPTH` を「近さ」1 本にまとめた。** `REQ-VDP-004` は
「`DIRECT` を動かすと 2〜5 kHz と Transient が同時に動く」を受入条件にして
いるので、`dsp.md` の当初の式（Transient は `DEPTH` だけの関数）では満たせ
なかった。`DIRECT` = 0.5 で従来と一致する。

**罠が 3 つ増えた。**

- **開き具合から dB を見積もると悲観的すぎる。** 「0.204 × 3 dB = 0.6 dB」は
  予算を越えるが、**110 Hz の純音は Presence 帯にエネルギーを持たない**。
  **機構を切った同じ走行と比べる**と 0.045 dB。**測る対象を間違えて、設計を
  作り直しかけた**
- **段のテストが零交差の上に落ちた。** 3 kHz は 48 kHz で 16 サンプル周期なので
  12 000 サンプル目はちょうど零交差。**段に掛ける相手が無く、対照実験まで
  1.00 になった**。周期の整数倍を避ける
- **対称なフォロワが非対称に見えた。** 立ち上がりを 63 % で止めてそこから
  立ち下がりを測ると 1 時定数が 0.54 τ になる（96 対 52）。**折り返す前に
  落ち着かせる**

### 設計の要点

**要件も `dsp.md` も決着している** —
[`REQ-VDP.md`](../plugins/vocal-depth/docs/requirements/REQ-VDP.md) と
[`dsp.md`](../plugins/vocal-depth/docs/specifications/dsp.md)。要件は先に
「設計の中心にある 5 つの判断」だけ読めば残りはその帰結。

**Air と正面から違うのは 1 点**: **原音が処理を通る**（`REQ-VDP-001`）。
遠ざけるとは Presence を削り高域を落とし Transient を鈍らせることなので、
直接音を触らずに距離は作れない。`MIX` 用の原音だけを最初に分岐して、
透明性の約束はそこに閉じ込める。**`MIX` はクロスフェード**（Air の加算型とは
違う）。

**`dsp.md` で決めた 5 つ**（計画書が投げていた問い。理由は各節にある）:

| 問い | 答え |
|---|---|
| タップ時刻を `DEPTH` で動かすか | **動かさない。** 重み包絡（σ = 0.45 のガウス窓）の中心を動かす。補間も detune も無い。**整数読みで済むので CPU も 4 分の 1**（クリックは別で、重みのスムージングが要った — 上） |
| タップの本数と時刻 | **10 本 × 2 チャネル。11〜89 ms の素数 ms を L/R 交互**（`VDP-1` の実測で 13 本 / 113 ms から縮めた） |
| オールパス | **3 段、`g` = 0.45、タップ列の前**（入力拡散） |
| ラウドネス正規化 | **固定 32 点のピンク重み格子の上で、振幅特性の 2 乗和を解析的に足して割る。** オールパスは総エネルギーを変えないので式に入らない |
| `DAMPING` の比 | **1.2 : 3.0 オクターブ**。全開で直接音 8.7 kHz、反射 2.5 kHz |

**共有クレートに上げるものが 2 つ出た**（計画書の「新規単位が無い」を直した）。
どちらも数十行なので単位は起こしていない:

- **`DelayLine` を `nxe-audio` へ** — `VDP-1` で**済んだ**
- **`biquad::Coefficients::magnitude`**（`VDP-3`、6 行）。信号を見ない正規化が
  振幅特性を要求する。**まだ書いていない**

**位置づけと計画。**

計画は [`../plugins/vocal-depth/docs/implementation/vocal-depth-plan.md`](../plugins/vocal-depth/docs/implementation/vocal-depth-plan.md)。
**`vocal-depth-core` クレートもこの単位で作る**（`VEL-1` / `SPK-2` /
`AIR-1` と同じ位置）。

**v1 で唯一の新規 DSP ブロック**で、**3 製品で共有される**（Vocal Depth /
Vocal Glue の `Ambience Glue` / Impact の `SIZE`）。`vocal-depth-core` に置き、
**Vocal Depth を知らない自立したモジュールとして書く** — `noise.rs` を Air で
そう書いたのと同じで、2 個目が要求したらファイルの移動だけで済む。

**ゲートは `VDP-1` ではなく `VDP-3`**（`DEPTH` 全域でラウドネス ±0.5 dB）。
連動する項が全部揃って初めて測れるので 3 番目。**耳ではなく単体テストで通る。**

## Air で分かったこと（`AIR-1`〜`AIR-13`）

**ゲートは通った。** `WIDTH` 全域でモノ和に櫛形が出ない（`REQ-AIR-008`）。
位相を回す処理を 1 つも置かない設計なので構造的にそうなる、を測って固定した。

| 何 | 実測 |
|---|---|
| モノ和の帯域比のばらつき | `WIDTH` 全域で **1 dB 未満** |
| `WIDTH` = 1 のモノ和 | −3.0 dB、相関 0 付近 |
| 核の帯域（4〜10 kHz）のレート差 | **0.39 dB 以内**（4 レート） |
| 4x の最悪ケースの折り返し | **−70.0 dB**（許容 −60） |
| `BLEND` の掃引 | **0.02 dB**（トリムを入れる前は 28.9 dB） |
| 上蓋の上へ逃げる量 | `FOCUS` +1 で **−30.2 dB** |
| 層の群遅延 | 4x で **12 サンプル**（0.24 ms）。原音には掛からない |
| `SURFACE` = 1 の層 | ピンク −18 dBFS に対して **−31 dBFS**（13 dB 下） |
| 保護（ピンク / 定常倍音列） | **0.00 dB**。ハイパスしたピンクで −12.00 dB |
| `BRIGHTNESS` の入力ゲイン非依存 | ±12 dB で **完全一致** |
| 段変化の継ぎ目 | 原音に対して **−46 dB** |
| ブロックサイズ 1 / 64 / 512 / 4096 | **ビット一致** |
| CPU（エンジン、4x / 512 / 48 kHz） | **47.2 µs**（予算 533、目標 250） |
| 同、`SURFACE` = 0 | **17.1 µs** — 4x のブロックを回していない |

**測定の側が主役だった単位。** 落ちたテストの大半は実装ではなく測り方の
間違いで、直したのは:

- **番兵は全フィールドを外す。** `set` はフィールドごとに「動いていなければ
  何もしない」ので、1 つだけ NaN にした番兵だと**残りの係数が初期化されない**。
  `width` が既定と一致していて層が完全な無音で出てきた
- **櫛形の対照実験に遅延を使うと通る。** 12 サンプルの遅延は 1/3 オクターブ帯
  より細かい櫛を作るので **0.9 dB しか出ない**。オールパス（設計が拒んでいる
  手法そのもの）で 6.6 dB
- **レート非依存を広い帯域通過で測ると測定側が歪む。** 14 kHz の 2 次ローパスは
  44.1 kHz でナイキストの 0.64、192 kHz で 0.15 に居る。0.53 dB のずれが出て
  **全部が測定の側だった**
- **蓋の上を測るフィルタは急峻でないと自分の裾を測る。** 1 段で −18.3 dB、
  10 段で −34.3 dB
- **`CHARACTER` を「3 倍音 ÷ 2 倍音」で測ると 1.7 % しか動かない。**
  膝が奇数次を増やすと同時にバイアスが偶数次も増やすので相殺される。
  **「3 倍音 ÷ 基音」で 0.150 → 0.248**
- **継ぎ目の測り方を 3 回間違えた**（`AIR-7`）。ノイズが混ざっていると
  測れない → 絶対値の跳びでは測れない → 高い層は 2 階差分でも測れない。
  **4 回目でようやく対照実験が差を出した**
- **整形済みのファイルへの文字列置換が 6 回黙って失敗した。**
  `.agents/rules/rust.md` にそのまま書いてある形で、**失敗が回を追って
  静かになった**: 1 回は**保護が配線されていないまま「全部 0.00 dB」という
  good に見える測定結果**（`SPK-18` の「効くはずのものが配線されていない」と
  同じ）、最後の 1 回は**解析の publish が丸ごと消えて窓が静止**した。
  コンパイルは通り、テストも全部通る。**置換のあとは grep する**

**上の 1 オクターブはレートに依存する（直せない）。** 16 kHz 帯で 3.83 dB、
低いレートほど明るい。48 kHz では 20 kHz のディジタルローパスがナイキストの
0.83 に居て、双一次変換が遷移をナイキストへ押し付けるため。**スカラの補正を
試したら、層全体の RMS は 0.72 → 0.30 dB になる代わりに核の 4 帯域が
0.39 → 1.26 dB に開いた** — 平らな誤差を傾きに両替しただけなので戻した。
実測値はテストに固定してある。

1. **「遠い近い」に聞こえるか**（`VDP-14` で作り直したところ）。直接/反射比は
   `DEPTH` 全域で **+25.6 → +2.3 dB**、直接音の広帯域レベルは **−9 dB** 落ち、
   HF は既定の `DAMPING` で **14.9 → 8.7 kHz**（`DAMPING` 全開なら 3.8 kHz）
2. **`DEPTH` を回して音量が動くと感じるか。** 測定は **±0.83 dB** が最悪
   （ピンクと声）。**予算 ±1.0 dB をほぼ使い切っている**ので、もっと効き幅が
   欲しいなら**許容をもう一段動かすか、Presence の可動域を縮めるかの判断**が要る

### 2. `VDP-13` — 既定値

**測れるものを先に測って `defaults.rs` に固定する**（`AIR-13` / `SPK-18` の形。
ラッパ側から `default()` を読むので、測る数と出荷する数がずれない）。
**`DEPTH` の中央が「素直なスタジオの距離」に聞こえること**が最終条件
（`REQ-VDP-021`）。今の既定は `DEPTH` 0.5 / `DIRECT` 0.5 / `ROOM` 0.5 /
`DAMPING` 0.5 / `WIDTH` 0.6 / `CLARITY` **0.0** / `MIX` 1.0 / `OUTPUT` 0 dB。

**`CLARITY` が 0 なのは意図。** 機構は測れているが**戻すのは復元**なので、
頼まれていないのに始めない。

### 3. 製品名を決める（`REQ-VDP-014`）

`NXE Vocal Depth` は Doubler と同じ記述的な名前で、Velour / Sparkleur / Air の
並びとは register が違う。**`CLAP_ID` は出荷後に変えられない**ので、
**最初のリリースまでに決める**。今は `com.nxe.vocaldepth`。

### 4. Advanced の偏差（`REQ-VDP-009`、まだ単位が無い）

**窓の問題ではない。** パラメータを 7 個増やすのでエンジン側の変更で、
**各偏差が数として何をするかを `dsp.md` がまだ書いていない**。窓は下段に
1 行増えるだけ。**要件から立て直す単位が要る。**

### 5. 急がないが決めておきたいこと

**オーバーサンプリングの倍率をホストレートから決めるか**（下の「残っている
宿題」）。192 kHz で使うなら効くが、上蓋と一緒に設計し直す必要がある。
**今すぐの回避策は `OVERSAMPLE` を 2x にすること**で、これは画面に出ている。

## 仮のまま残してある定数

**動かす理由が出てから触る。** Velour の既定値は `VEL-17` で決めた（`DRIVE` 80 /

**Sparkleur の 33 個はまだ仮**（`SPK-18`、上の表）。

| 何 | 聴きどころ |

| Guard のしきい値 −8 / −14 dB | 普通のボーカルで**動かない**のが正。動くなら厳しい。**Sparkleur では同じ形が破れていた**（`SPK-18`）— Velour でも広帯域素材で測り直す価値がある |
| `EMOTION` の係数 3 つ | 0.50 / 0.40 / 0.30。声量差で質感が変わるのが**分かるが不安定でない**か |

## Velour で踏んだ罠（同じ形を 3 回やった）

**テスト信号の周波数を「周期数」で書くな。** 周期数はバッファ長とサンプルレートに
依存するので、間違えても落ちず「符号が逆の測定値」として出てくる。`VEL-2` /
`VEL-8` / `VEL-9` で 3 回踏んだ。**`harmonics::tone(amplitude, hz, rate, length)`
と `bin_of(hz, rate, length)` を足したので、以後は周波数で書く。**

**「往復すれば分かる」は嘘のことがある。** オーバーサンプラの位相の割り当てを
逆にしていたが、往復テストは通り低域の正弦も無事に戻ってきた。壊れていたのは
**その間に居る非線形が見る信号**で、イメージが −88 dB ではなく −24 dB だった。
`the_upsampler_leaves_no_image` がそれを固定している。

**エンベロープが絡むものはブロックごとに `set_shape` して測れ。** テストヘルパ
`rendered` は最初のサンプルの前に 1 回だけ呼ぶので、検波器はまだ無音しか
見ていない。`EMOTION` の向きが**全部逆に測れた**。ホストと同じ形で回す
`blocked` を別に用意してある。

**テストが「何も検出できないまま通る」ことがある。** `VEL-10` のジッパーの
テストは、可動域の 25% を 1 段で動かしても通っていた（エンジンにパラメータで
跳ねるゲインが 1 つも無いので、実は正しい）。**測定が失敗できることを同じテスト
の中で確かめる**行を足してある。

**引き算で「足した層」を取り出すな。** `出力 − 原音` は原音の方が大きいと層の
精度をほとんど捨てる。`SOLO` を全部オンにして層を直接取る。

## Sparkleur で踏んだ罠

**測定用のノイズに DC が乗っていた**（`SPK-18`）。
`(state >> 8) / 2^23 * 2.0 - 1.0` は 24 ビットを 2^23 で割ってから 2 倍するので
値域が `-1..3`、平均 +1。ピンク化の 1 段目の極（0.99765）は **DC で 425 倍**
なので、「ピンクノイズ」がほぼ定数になっていた。**band 0 が全エネルギーを
持つ**形で出て初めて分かった。**De-Harsh の測定は無事だった**（参照帯も検出帯も
帯域通過なので DC が届かない — 測り直して同じ数字）が、**エンジンのレベル掃引と
`CHARACTER` のドリフトは全部やり直し**。テスト信号は自分でも測る。

**「効くはずのもの」が配線されていないことがある**（`SPK-18`）。
`Character::trim_db` は補間されて `pub` で出ているのに、**エンジンが一度も
読んでいなかった** — 軸のレベルを直す手段が最初から効かない状態だった。
`SPK-5` の完了条件は「±1.5 dB 以内（トリム 0）」で、**0 のものが効くかどうかは
0 では測れない。**

**トリムに入れる数字が「無い」こともある**（`SPK-18`）。4 素材で測ると持続音は
3 つとも 0.13 dB 以内で、**動くのはハットだけ**（2.4 dB）。ハットを平らにする
トリムは他の 3 つを同じだけ逆に傾ける。動く理由は CRUSH の 6:1 が POLISH の
1.5:1 より深く潰すからで、**要求している処理そのもの**。**「ずれているから
補正する」の前に、そのずれが仕事かどうかを見る。**

**「一番近い名前」は名前が等間隔に並んでいるときしか正しくない**（`SPK-18`）。
`CHARACTER` のアンカーは POLISH 0.0 / GLOSS 0.5 / CRUSH 1.0 で、**両端の 2 つが
端に、GLOSS が真ん中**にいる。「一番近いアンカーを表示する」だと**GLOSS が軸の
半分を取り、他の 2 つが 4 分の 1 ずつ**になり、既定の 0.27 が `GLOSS 27 %` と
出ていた — `REQ-SPK-006` が「POLISH 寄り」として選んだ値なのに。**軸を 3 等分**
して境界を 0.33 / 0.67 にした。**音ではなく読み値を動かした**（0.27 の音が
悪いという話ではなかった）。

**同じ規則は両端でも壊れていた**（`SPK-18`）。`POLISH 0 %` は「polish が 0」と
読めるが、実際は**一番 polish が強い**設定。**持ち越し宿題には「既定値と読み値の
衝突」1 件として記録してあったが、開けたら規則そのものの欠陥が 2 つあった。**
パーセントはパラメータ自身の値のままにしてある — 区画の中での進み具合に
書き換えると、ホストのオートメーション表示と**1 つのコントロールに 2 つの違う
数字**が出る。

**共有した機構は片方の製品のチューニングを黙って運ぶ**（`SPK-18`）。De-Harsh は
Velour の相対検出器をそのまま借り、**参照帯 300 Hz〜8 kHz まで借りていた**。
それだと Sparkleur の検出帯 1.5〜5 kHz が**自分の参照帯の中に入る**ので、
検出帯を +10 dB 持ち上げると参照帯も 6 dB 上がり、**10 dB の harsh が 2 dB に
しか読めない**。しきい値 −8 dB はどの広帯域素材の比よりも下にあり
（pad −6.96 / pink −4.06 / white −3.03）、**ピンクノイズから既定値で 1.3 dB
引いていた**。参照帯を検出帯の下（200 Hz〜1.2 kHz）に移すと読み取り幅が
2.04 → 7.12 dB。**`SPK-1` で機構を分けたのはこのためだったのに、値の方で
同じ轍を踏んだ。**

**「普通の素材で動かない」は 2 音のテストでは守れない**（`SPK-18`）。De-Harsh の
既存テストは 400 Hz と 2.8 kHz の 2 音で「バランスの取れた信号」を作っていたが、
検出帯にほとんど何も無い信号は**どんなしきい値でも通る**。広帯域（ピンク
ノイズ）で測って初めて 4 dB ずれていることが出た。**しきい値のテストは
広帯域で書く。**

**相対検出器は立ち上がるまで無限に harsh に見える**（`SPK-18`）。参照フォロワが
0 から始まるので、サンプル 0 から測るとピンクノイズが上限 12 dB を引く。
同じ形が Sparkle のゲートにもあって、**信号が始まること自体がトランジェント**
なのでパッドでもゲートが 1.000 を記録した。**落ち着くまで（100〜250 ms）
捨ててから測る。**

**末尾の 1 サンプルは分布ではない**（`SPK-18`）。最初は「走らせ終えたときの
引き量」で素材の比を出していたが、ノイズではそれは 1 つの偶然の瞬間。
p50 / p95 / max を並べたらしきい値を置くべき場所が変わった。

**DSP で落ちたテストは 6 本中 4 本が「実装ではなく期待値」の間違いだった。**
落ちたら先に実測を並べて理論値と突き合わせるほうが速い。**逆に UI の欠陥は
テストが 1 本も落ちない** — 実機で見るまで 3 つとも分からなかった（下の
`SPK-15` の 3 つ）。

**分割の裾は 24 dB/oct とは限らない**（`SPK-2`）。木構造なので各帯域は自分の
境界だけでなく**上流の全部のハイパス**を通っている。band 5 の 6 kHz より
1 オクターブ下は `HP(1500)` がまだ効いていて 30 dB/oct で落ちる。24 dB/oct を
測るなら境界が 1 つしか効かないところ。**帯域の幾何中心も 0 dB ではない**
（band 2 は 1.7 オクターブ幅で中心が −1.5 dB）。

**符号を足したら塗りの向きも足す**（実機で判明、`SPK-15`）。`SPK-10` で
`Band::delta` を符号付きにしたのに、**区画の塗りが床から生えたまま**だった。
`GAIN` が全部 0 dB のとき下半分が青一色の塊になり、`SPK-13` で引いた unity の
線はその下に完全に隠れていた。**テストは 1 本も落ちない** — `live()` の算術は
正しく、間違っていたのは描画の基準点だけ。**寸法と塗りは実機でしか分からない。**

**1 次のフィルタは 0 に到達しない**（`SPK-16`）。無音が続くと Sparkle の
ゲートが **1.3e-42** に落ち着いた。画面上は「閉じきらないゲート」。**描けない
大きさを切ったら 0 にする。** 同じ形が検波器と Guard のエネルギーにも残って
いるが、**そちらは放っておいてよい** — `SPK-17` で調べたところ
**nih-plug が `process` の前後で FTZ を x86 でも aarch64 でも有効にする**ので、
ホストの中ではデノーマルになりようがない（無音に落ちていく経路の実測も
働いているときと同じ 110 µs）。

**NaN 1 個で全部止まる場所は 1 つとは限らない**（`SPK-9`）。Velour の
`VEL-10` は検波器で見つけたので Sparkleur も検波器は守っていたが、**分割その
ものが信号経路**なのでクロスオーバーの biquad がラッチした。**入口で 1 回
消毒する**（40 個のフィルタそれぞれに番人を置くより安い）。原音は消毒しない —
通り道なので NaN を送ってきたホストには NaN が返る。

**レート非依存を定在音で測るな**（`SPK-9`）。IIR オーバーサンプラの遅延は
**サンプル数で固定**なので、層と原帯域が足し算される位相がレートで回る。
7 kHz の正弦で 48 対 96 kHz が 1.0 dB ずれて見えるが、分割だけなら 3 レートで
**完全に同じ数字**。**ノイズで測る。**

**保護は `SPARK` に乗せる**（`SPK-8`）。De-Harsh を `SPARK` と独立にすると、
**`SPARK` = 0 でも平坦にならない** — 2 kHz の単音は自分の参照帯に対して
しきい値を超えているので引かれる。`REQ-SPK-008` の
`Spark ↑ → Harshness Suppression ↑` がまさにその掛け算で、**要件を読み返したら
答えが書いてあった**。保護を足すときは「量の macro に乗るか」を先に決める。

**非対称なフォロワを比の分子に置くな**（`SPK-6`）。仕様の Sparkle は fast を
1 ms / 40 ms の非対称にしていたが、非対称な追従は平均とピークの間に座るので
（下の `SPK-3`）、対称な slow との比が**定常音でも 3 dB 出る** — ゲートが
0.44 開いたままだった。**フォロワは両方対称にして、リリースは比の後ろの
ホールドに置く。** 同じ形は「2 つの検波器の比」を取るところ全部にある。

**有限の dB は有限のゲインではない**（`SPK-4`）。hostile テストが `GAIN` に
1e9 dB を渡したとき、dB は有限のまま `linear()` が無限大を返した。
**Sparkleur でここまで唯一の「実装側の」バグ**（他はどれもテストの期待値の
間違い）。`MAX_GAIN_DB` = ±48 dB で蓋をしてある — **趣味の制限ではなく算術の
制限**なので、`CHARACTER` の値を触るときに動かすものではない。

**上げコンプの上限と床はどちらが先に効くか分からない**（`SPK-4`）。既定の床
−60 dB では POLISH も GLOSS も `CEILING` に届かず（実測 4.0 / 8.0 dB 対
上限 6 / 9 dB）、CRUSH だけが当たる。**聴き手が当たっている制限が `CHARACTER`
で入れ替わる**ので、`SPK-18` で数字を動かすときはここを見る。

**検波値は帯域の RMS ではない**（`SPK-3`）。非対称な 1 次追従は平均に落ち着かず、
**RMS の +0.05〜+2.54 dB** に座る。位置を決めるのは attack/release の比だけ
（比 4 で +0.05〜0.9、比 20 で +2.5）。素直なコンプの挙動だが、**しきい値を
計算で出せない**ということでもある — `SPK-18` を耳でやる根拠。

**定常正弦は時定数の床を測る道具として弱い**（`SPK-3`）。50 Hz では release の
20 ms が単独で読み値を持ち上げるので、attack が 1 ms でも 33 ms でもリプルは
1.0 dB のまま変わらない。**「対照実験が差を出さない」形の失敗**で、`VEL-10` の
「測定が失敗できることを同じテストで確かめる」行がそれを捕まえた。差が出るのは
**ステップ応答**（床のある帯域と無い帯域で 33 倍）。

**仕様の数字は 4 回動いた。** `k` の上限 20 → 6 → 8、`bias` のレベル補正
6 dB → 0、`DENSITY` のメイクアップの基準 full scale → `REFERENCE_DB`。
どれも実測が仕様を否定した結果で、**理由と実測値を `dsp.md` と
`velour-plan.md` に残してある**。同じ数字を触るなら先にそこを読む。

## Doubler で踏んだ罠

このリビジョンの vizia には**コンパイルも通り、エラーも出さず、何もしない**
ものがある。全部 [`../.agents/rules/vizia.md`](../.agents/rules/vizia.md) に
理由付きで書いてあるが、特に刺さりやすいのは:

- **CSS の `font-size` は単位を受け付けない。** `12px` はパース失敗で宣言ごと
  捨てられ、既定の 16 px になる
- **`cx.add_timer` は baseview で一度も発火しない。** 周期処理は `cx.spawn`
- **未指定のサイズは `Auto` ではなく `Stretch(1.0)`**
- **当たり判定を持つ子は親の押下を飲む**

**「直したつもりで直っていない」を疑う前に、まず二分探索する** —
この開発で一番時間を溶かしたのはそこ。

## 次にプラグインを足すとき

`docs/specifications/architecture.md` の「新しいプラグインを足す」に手順がある。
`nxe-ui` と `nxe-dsp` はそのまま使える。

**3 個目は Sparkleur**（マルチバンドダイナミクス + Harmonic Sparkle）。
順序の根拠は [`implementation/roadmap.md`](implementation/roadmap.md) の
「Velour の後」。材料は `SPK-1` で `nxe-audio` に移してある。

**「上げるのは 2 個目が要求してから」は当たったが、境界は 2 か所ずれた**
（`SPK-1`）。**測定ヘルパの `harmonics` も一緒に動く** — 移すモジュールの
テストが全部それで書かれていて、`nxe-audio` は `velour-core` に依存できない。
**耳で決めた数は残す** — `envelope` は機構だけ移し、attack 5 ms /
release 150 ms と `REFERENCE_DB` は `velour-core` の `envelope::vocal()` に
置いた。4 個目を足すときも同じ 2 つを見る。

## リリースのしかた

```bash
git tag -a doubler-v0.1.3 -m 'NXE Doubler 0.1.3'
git push origin doubler-v0.1.3
gh release edit doubler-v0.1.3 --title 'NXE Doubler v0.1.3' \
  --notes-file notes.md --draft=false
```

タグからプラグイン名とバージョンを読み、3 OS でビルドして**下書き** Release に
zip を付ける。**バージョンはプラグインの `Cargo.toml` が持つ**ので、タグと
食い違うと CI が落ちる（わざとそうしてある）。**`-core` も同じ出荷単位**なので
一緒に上げる。

**タグは 1 本ずつ push する。** GitHub は **1 回の push に 4 本以上タグが
入っていると run を 1 つも作らない** — 4 本まとめて出したとき、タグは全部
上がったのに**ビルドが 1 つも始まらず、どこにもエラーが出なかった**。
やり直すには remote のタグを消して 1 本ずつ push し直すことになる。

**戻り道を用意してある**: ワークフローに `workflow_dispatch` を足したので、
タグを消さずに `gh workflow run release -f tag=<tag>` で回せる。
